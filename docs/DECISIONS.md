# 設計判断記録

リポジトリ `watabegg/slidev-stage-hub` は、Slidev によるプレゼンテーションの作成、実行、配信を統合する基盤である。本リポジトリは公開ソースコードとして開発中であり、npm レジストリへのパッケージ登録や各 OS 向けネイティブバイナリの一般配布、ライセンス選定は未完了の開発中プロジェクトである。本書では、本システムのアーキテクチャにおける主要な技術的判断、採用理由、およびそれに伴う制約やトレードオフを記録する。

---

## 1. モノレポ構造と実行環境ごとの責務分離

pnpm ワークスペースによるモノレポ構成を採用し、実行基盤ごとに責務を物理的に分離している。デスクトップ表示環境の `apps/stage` では Rust core を状態の正本（Single Source of Truth）とし、`src-tauri` がホスト側の入出力、認証、発表者ノート処理を担当し、`src` の TypeScript コードは表示フレームと UI 操作に特化する。`packages/hub` は Slidev のビルド処理、画面描画を伴わないヘッドレスクライアント、任意の Vue フロントエンド実装を提供する。エッジ環境の `apps/hub-worker` には Cloudflare Workers 向け実装、ブラウザランタイム、ビルド用 Node スクリプトを配置する。共通層には純粋な通信規約を定義する `packages/protocol`（contracts と bridge）、解析・パッチおよび `/clicks` 処理を担う `packages/slidev-adapter`、環境準備・接続・設定サービスを提供する `packages/stage-tools`、薄い CLI アダプターである `packages/cli` を設けている。

デスクトップ実行、Web ビルド、エッジ配信、共通プロトコル定義では求められる実行要件が異なる。境界を物理的に分けることで、特定環境に依存したコードが他方へ漏れ出す事態を防ぎ、安全なモジュール構造を維持するためである。

トレードオフとして、共通規約の変更時には関連パッケージ全体の同期更新が必要となる。また、パッケージ間の境界検査を厳格に維持するための管理コストが発生する。

## 2. 共有モジュールグラフの導入と互換グループによるビルド分離

複数の Slidev 資料をまとめて出力する際、共通利用可能なモジュールを単一のモジュールグラフとして共有出力する。ただし、同一互換グループ（Slidev のバージョン、テーマ、`setup` スクリプト、およびコンパイル設定が一致するもの）に属する資料間でのみ共有を行い、これらが異なる資料はビルドプロセスを物理的に分離して独立した文書として出力する。Slidev 本体の依存関係は `52.15.2` および `53.0.0` の 2 バージョンのみに厳密に対応し、非公開内部実装に対するパッチは文字列署名検証とともに `slidev-adapter` へ隔離して署名不一致時に処理を停止する。

重複する JavaScript アセットを削減して配信効率を高めつつ、異なるテーマの CSS 競合や `setup` スクリプト、コンパイル設定の実行副作用が他方のスライドへ干渉する事故を防止するためである。また、Slidev 本体の内部仕様変更による予期せぬ破壊を検知して安全に停止させるためでもある。

設定やテーマが異なる資料間ではバンドル共有の恩恵を受けられない。また、厳格に対応している上記 2 バージョン以外の Slidev に対する動作保証はなく、未対応バージョンでは動作しない。

## 3. Rust Core による状態一元管理と予備フレーム描画

スライドの現在ページやクリック進行といった状態の権威的な正本をすべて Rust core で一元管理する。UI レイヤー（TypeScript）側は Rust core からのスナップショットに基づき表示状態を保持するが、正本を重複して保持しない。同一資料内のページ送りやクリック操作では既存の iframe を維持して描画を更新し、別資料への切り替え時は非表示の予備フレーム（iframe）をあらかじめ生成して描画完了の確認応答（ACK）を待ってから表示フレームと入れ替える。この通信ではトークン、世代番号、リビジョン情報を用いて遅延した古い ACK を拒否する。デスクトップ UI には Tauri を採用し、WebKit 互換性の検証を Node.js テストで代替せず実機環境で確認する。

資料切り替え時に発生する画面の空白やちらつきを排除し、非同期通信下での状態不整合を防ぐためである。また、レンダラー（WebKit）固有の描画差異を確実に捉えるためである。

予備フレームの保持により一時的にメモリ消費量が増加し、切り替え完了までに描画応答待ちの遅延が発生する。また、WebKit 特有の問題検証には実機テスト環境の実行が必須となる。

## 4. 発表者ノートの秘匿と端末ローカル管理

公開用の配信マニフェストには、ローカル環境のファイルパスや私有の発表者ノートを一切含めず、非公開レシート（private receipt）と Stage 側の内部管理領域に完全に分離する。ローカル資料のノート更新は、あらかじめ指定された許可ルートディレクトリ内に存在し、ハッシュ照合が一致する場合に限り、各スライド末尾の既存コメントブロックを上書き更新する。リモートから取得した資料のノートは、オリジン、資料 ID、ページ番号ごとに端末内のローカルサイドカー領域にのみ保存し、ネットワーク外部へ送信しない。スライド操作は単純なクリック構文のみに対応し、複雑な構文のネイティブ対応は保守的に拒否する。Web 側で表示可能な表現とネイティブ側で安全に扱える構文を混同しない。

登壇用の非公開メモや作業ファイルパスが外部へ流出するセキュリティ事故を防ぎ、構文解釈の破綻による表示不具合を未然に防ぐためである。

リモート資料に対する発表者ノートは端末間で自動同期されない。また、Slidev の高度な独自構文や動的スクリプトはネイティブ環境では扱えず、機能が制限される。

## 5. CLI プロセスの独立性とヘッドレス Web クライアント設計

Stage および Hub の主要ロジックを、CLI 実行プロセスから独立したライブラリ構造として実装している。CLI ツール内では、設定基準ディレクトリ（settings root）と作業ディレクトリ（cwd）からの相対引数を明確に区別してパスを解決する。外部検証用としてプライベート tarball を用い、公開コマンド名として `hub` および `stage` を提供する。Web 向けには、画面描画を伴わないヘッドレスな `CatalogSource` およびクライアントを提供し、Vue 用のコンポーネントマウント（`mountHub` や `mountNavigation`）を任意利用の拡張として位置づける。エントリーポイント、スタイルシート、データ取得元は自由に差し替え可能とし、無条件な DOM マウントやグローバル CSS の適用を排除して UI コードの重複を避ける。

CLI 実行時の作業ディレクトリの違いによるパス解決の誤りを防ぐとともに、Web アプリケーション側で独自の UI やスタイルへ安全に組み込める柔軟性を確保するためである。

ヘッドレス構成を採用しているため、既存の Web アプリケーションに組み込む際は、マウント処理やデータ接続を実装するコードが呼び出し側に必要となる。

## 6. Workers R2 と Durable Objects によるアトミック配信とリビジョン固定

Cloudflare Workers 上で、R2（静的アセット保管用 FILES）と Durable Objects（DeckVersions migration v1 によるバージョン管理 VERSIONS）を組み合わせた配信基盤を採用している。公開フローは「begin（公開開始宣言）→ アーティファクトとマニフェストの配置 → インデックスマーカー作成 → commit（公開確定）」の順序を強制する。最新の begin セッションのみが commit を実行でき、途中で失敗した場合は現在の配信バージョンを維持する。各リリースは内容に基づく SHA-256 ハッシュをリビジョン識別子として管理するが、ハッシュ値自体が改ざん不能性を保証するものではない。また、失敗時に現在の配信バージョンを維持する仕組みはあるものの、過去バージョンへ任意に戻すロールバック機能は未実装である。Stage の native-player v2 では、`native-player.json` において `playback.kind = "revision-query"`、パラメータ名 `revision` を指定して接続中リビジョンを固定する。接続中に新しい版が公開されても接続先リビジョンは維持され、再接続前に新バージョンを通知する機能はない。新しいリビジョンを採用して再接続した際に、既存ノートとリビジョンの不一致に関する警告を表示する。カタログ API（Catalog v1）は全ページを順次取得し、Bridge v1 および設定スキーマ（config v1）の後方互換性を不変として維持する。動的モジュール読み込みは、同一オリジンかつ不変リビジョンを検証する URL ガードで保護する。

登壇中にバックエンドの資料が更新されてアセットの不整合が生じ、スライド表示が破損するトラブルを防止するためである。また、安全で一貫した公開フローを実現するためである。

クラウド実環境への配備および Cloudflare Access を用いた本番認証の受け入れ試験は別工程となっており、現行の検証はローカルシミュレーション環境を前提としている。また、過去バージョンへの任意のロールバック操作は行えない。

## 7. 認証ヘッダーの隔離とトークン保護

認証トークンは、通信先オリジンを限定したファイルパーミッション 0600 のプライベートヘッダーファイルとして管理する。通信経路は HTTPS またはローカルループバックアドレス宛の HTTP に制限する。Node.js 側は接続メタデータ取得時に認証ヘッダーを付与し、常時ローカルプロキシとして動作するわけではない。Rust 側では認証が必要なリモートアセットの取得をプロキシし、認証不要な資料は直接取得する経路を備え、Web ランタイムの JavaScript 環境へ直接生トークンを露出させない。HTTP リダイレクトは安全のため一律拒否し、TLS 証明書の正当性検証を維持する。シングルサインオン（SSO）、多要素認証（MFA）、および OS のキーチェーン連携には現時点で対応していない。

ブラウザ側スクリプトの脆弱性や外部リダイレクトを悪用したトークン窃取を防ぎ、ローカル環境での安全な通信を確立するためである。

認証付きリモート資料の取得には Rust プロキシを経由させる構成が必要となり、ネットワーク処理の管理が複雑化する。また、OS ネイティブの安全な認証鍵ストアや企業の SSO / MFA 環境は利用できない。

## 8. コード境界の静的検査と多層的な環境分離検証

pnpm ワークスペース全体で Oxlint、Oxfmt、strict TypeScript、`vue-tsc` による静的解析を常時適用している。専用の境界検査スクリプトによりモジュール間の循環参照や禁止インポートを機械的に遮断し、例外を一切認めない。特に、本番パッケージから実験用コードへのインポートは厳格に禁止している（実験用コードから本番パッケージへのインポートは許可される）。動作検証においては単一の環境に依存せず、Node.js クリーンコンテナ、プライベート tarball による外部インストール検証、local workerd（エッジ動作環境）、Rust ネイティブテスト、実機 Tauri / WebKit 環境の各層を分離してテストを実施している。

長期的な開発に伴うパッケージ依存の肥大化や循環参照を防ぎ、各プラットフォーム特有の実行時不具合を実行環境の違いを踏まえて早期に検出するためである。

ビルドおよび検証作業には外部パッケージの取得とネットワーク接続が必要であり、オフライン環境でのビルド動作は保証されない。

## 9 共通サーバー・実行環境・永続化・デプロイの分離

### 9.1 背景と動機

Cloudflare 環境（Workers、Durable Objects、R2）への過度な依存によるコンパイラや配信処理の二重管理リスクを解消するため、システムを単一の共通コアとポート（インターフェース）に再編し、実行アダプター、永続化層、デプロイ構成を分離した。無関係なフレームワーク刷新は避け、既存の HTTP エンドポイント契約、配信プロトコル、CLI、および Durable Objects の SQL 状態やマイグレーション v1 との完全な互換性を維持している。

### 9.2 コアとアダプターの設計境界

共通コア（`packages/server`）は `createHubServer(options)` を提供し、`fetch` ハンドラーオブジェクトを返す。環境非依存を徹底するため、TypeScript 設定は ES2022 および DOM ライブラリのみを参照し、型宣言 `types` は空配列（`types: []`）として Node.js や Cloudflare 固有の型を排除した。

### 9.3 永続化層の設計判断

永続化層ではオブジェクトストレージと配信ストアを独立して合成可能とした。PostgreSQL 配信ストアでは、既存の Durable Objects と同等の配信セマンティクスを維持するため、ポインタ専用テーブルへの過剰な分割を避けてマニフェスト全体の JSON データを `jsonb` カラムに直接格納する方式を採用した。世代管理には `bigint` の世代番号を用い、最新の開始要求を優先する「latest-begin-wins」規則を適用する。新たに成功した `begin` はその後の公開が失敗しても過去のトークンを無効化するが、ストレージ更新に至らず失敗した `begin` は既存トークンを無効化しない。デッキ間を跨ぐグローバルトランザクションや、CAS によるオブジェクトストレージ単体での配信管理は設けていない。

### 9.4 ローカルと本番の分離

ローカル開発用のファイルシステム成果物保存やインメモリ配信ストアは本番環境での利用を明示的に禁止し、本番向けには S3/GCS および PostgreSQL を選定した。SQS、Pub/Sub、Redis など外部メッセージブローカーや DynamoDB/Firestore、AWS Lambda/API Gateway 向けアダプターの採用は見送っている。公開ジョブは公開状態と同じトランザクションで更新できる既存の保存先に置く。

### 9.5 ランタイム固定による過去リビジョンの表示互換性維持

最新の静的アセット更新による過去スライドの表示崩れを防ぐため、公開時のランタイム一式を不変スナップショットとして保存し、リビジョンごとにランタイムIDを固定（Runtime Pinning）する方式を採用しました。新規SDKや外部ストアは導入せず、既存のArtifactStore（Cloudflare R2、Amazon S3、Google Cloud Storage、ローカルファイルシステム）で共有・再利用します。公開時は整合性ハッシュ検証と条件付き不変書き込みを行い、準備完了記述子 `runtime-index/<id>.json` を最後に配置することで、失敗時も直前の公開状態を維持します。

トレードオフとして、自動ガベージコレクション（GC）を行わず無期限保持するためストレージ使用量が増加します。また、本方式はアーカイブの維持を前提とし、将来のサーバーやプロトコル変更に対する永続的な互換性までは保証しません。運用の詳細は [guides/platforms.md](guides/platforms.md)、検証結果の集約状況は [results/runtime-pinning.json](results/runtime-pinning.json) を参照してください。

### 9.6 検証状況とスコープ境界

実環境の AWS、GCP、Cloudflare Access における受け入れ検証やクラウド環境への実デプロイは未実施であり、今回の決定範囲から除外している。最新のローカル検証結果は [platform-portability.json](results/platform-portability.json) に集約されており、既存の [final-regression.json](results/final-regression.json) に含まれるネイティブ検証結果は過去のスナップショットである。各プラットフォームの詳細な構成仕様については [プラットフォーム導入ガイド](guides/platforms.md) を参照のこと。

## 10. 公開状態とジョブを同じトランザクションで更新

非同期公開では、ジョブの受付、公開世代の割り当て、既存ジョブの supersede、公開 pointer の更新を整合させる必要がある。そのため provider-free な `packages/server` に API と runner を置き、各アダプターでは公開 commit とジョブ状態を同じトランザクションで更新できる保存先を使う。Cloudflare は既存 `DeckVersions` Durable Object の SQLite トランザクション内で公開状態とジョブを扱い、alarm で起床する。Node/PostgreSQL は公開ストアとジョブストアを同じ PostgreSQL トランザクションに参加させ、worker は `SKIP LOCKED` polling で job を claim する。

カスタムアダプターの実装者は、publication commit と job transitions が同じトランザクションに参加する store を用意する必要がある。データベース接続情報を共有するだけでは、公開状態とジョブ状態の原子性は保証されない。first-party store は terminal publication finish と同じトランザクションで、デッキ単位の cleanup 要求を記録する。Node worker と既存の Cloudflare alarm がこの要求を消化し、最大100件の terminal leaf job と最大100件の private input deletion をデッキごとにローリング24時間あたり1回処理する。残作業や失敗は保留され、次の日次枠で再試行する。外部 queue、cron、global periodic sweep は設けず、optional な `PublicationJobMaintenanceStore.automatic` port により custom store のソース互換性を保つ。

完了から30日を経た job と未参照 private input は、恒久 tombstone と durable input-delete outbox を使って整理する。公開リリースと runtime は対象外である。導入時点ですでに完了している履歴は自動要求に登録されないため、後続 publication がないデッキやすぐ整理する場合は認証付きの上限付き `hub jobs cleanup` を使う。この手動経路は自動処理の日次枠を消費しない。クラウド実デプロイと live acceptance は未実施であり、保持契約と検証状況は[公開ジョブガイド](guides/publication-jobs.md)および[自動保持記録](results/publication-jobs-auto-retention.json)を参照してください。

## 11. Stage の資料一覧と発表操作

Stage はサムネイルと公開 frontmatter を使う資料一覧から開く。既存の Hub カタログクライアントで全ページを検証・取得し、接続時の資料レジストリに含まれる資料だけを選択可能にする。カタログ取得はホストが固定した通信先を使い、認証付き接続では既存プロキシを通す。一覧の取得に失敗した場合も資料 ID から開けるようにする。

発表中の誤操作を減らすため、スライド本文のクリックでは進めず、明示的な操作ボタンとキーボードを使う。アプリの外枠は OS に依存しない明るい配色とし、操作アイコンにはアクセシブルな名前と補足を付ける。ノートの保存契約は変更せず、ローカル資料の既存ノートがないページは編集不可とする。保存先は保存ボタンの補足に示し、内部エラーや通信状態を通常画面へ常時表示しない。
