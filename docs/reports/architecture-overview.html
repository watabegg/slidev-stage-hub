ワークスペース構成とプロジェクトの全体像

本リポジトリは、スライド発表を行うデスクトップアプリケーション「Stage」と、スライド資料を収集・配信する静的Webライブラリ「Hub」、および両者を結ぶ通信規約「protocol」を中心に構成されています。リポジトリ全体は pnpm のワークスペース機能を利用したモノレポ構造となっており、ルートおよび5つの子プロジェクトを合わせた計6つのプロジェクトが含まれています S01。

Hubの静的ポータル機能と表示仕様

Hub のフロントエンドは Vue 3 を採用した静的ライブラリとして実装されており、複数のスライド資料を一覧化して Web ブラウザ上で閲覧できるポータル画面（ホーム）を提供します S02。

ホーム画面では、各スライドのタイトル、説明文、subtitle、著者名、日付、tags、総スライド枚数、サムネイル画像が表示されます。ただし、コンポーネントの実装上は subtitle または description のいずれか一方のみを表示する分岐となっており、日付の表示についても「公開日」などの固定的な意味付けは定義されていません S02。

資料の整理機能として、ディレクトリ階層を反映したカテゴリツリーが生成されます。利用者は特定のカテゴリやその配下の子孫カテゴリを選択して表示対象を絞り込むことができます。また、各資料の個別ページへの遷移リンクに加えて、個別資料の表示中にはホームへ戻る常設リンクが配置されます（iframe 内に埋め込まれて表示されている場合は非表示になります）。画面レイアウトはスマートフォン表示にも対応しています S02。

現時点での Hub は静的ファイルの配信に特化しており、以下の機能は実装されていません S02。

  • テキストによる全文検索やキーワード検索機能
  • 資料一覧の動的な並べ替え機能
  • ブラウザ上でのスライド編集や新規アップロード機能
  • 管理画面やユーザーアカウント管理機能
  • Hub 自体に付随する認証サーバーやデータベース

ホーム画面の読み込み時点では Slidev 本体のランタイムはロードされず、利用者が特定の資料ページへ移動した段階で初めて各スライドのランタイムがロードされます。通常の Web 閲覧環境において別の資料へ移動する場合は、通常の Web ページ遷移（文書遷移）が行われます S02。

カタログ自動生成とバンドル共有ビルド

Hub では、配置された Markdown ファイル群から自動的にメタデータを収集し、最適化されたバンドルを生成する仕組みを備えています S03S04。

カタログ生成スクリプトは、対象ディレクトリ内の Markdown ファイルを再帰的に探索します。ファイルパスに応じて資料 ID が決定され、例えば foo/slides.md や foo.md はどちらも foo という資料 ID に変換されます。探索時には、隠しフォルダ、assets、public、node_modules ディレクトリ、および README.md や AGENTS.md といったドキュメント類が自動的に除外されます。探索結果の中で資料 ID の重複が検出された場合、カタログ生成処理は失敗します。また、資料のカテゴリ分類は配置されているフォルダ構造に基づいて決定されます S03。

スライド資料のバンドル処理では、1回のビルドプロセスで複数資料の仮想モジュールを個別化しつつ、互換ランタイムを共有する機構が実装されています。Slidev CLI および client の内部で使われている resolveOptions や ViteSlidevPlugin を直接参照し、Vue Router の base パスや同期チャネルを資料ごとに個別調整しています。Slidev の内部実装に依存した構成となっており、公式 CLI の単なるラッパーではありません S04。

テーマ管理とオフライン資産の生成仕様

Hub で利用されるスライドテーマと、生成された成果物のオフライン配備仕様は以下の通りです S05S06S07。

標準環境では、公式に公開されている @slidev/theme-default 0.25.0 および Slidev CLI / client 53.0.0 が使用されます。別テーマである watabegg 1.2.1 は専用のサンプルプロジェクトで明示的に選択されており、元のテーマリポジトリに変更を加えることなく利用されています S05。

この examples/watabegg に配置されたデモ資料は、表紙（cover）、FigureGrid とローカル SVG および QuestionList を組み合わせた 2 カラム構成（2クリック分）、区切り（section）の計3ページで構成されています。標準で提供される4つのスライド資料とは混在させず、ビルド出力先ディレクトリおよびローカルサーバーのポート番号（4175）を分離して管理されており、デフォルトのテーマ設定には影響を与えません S06。

オフライン環境での再生を支援するため、Hub にはアセットの事前準備スクリプトが用意されています。Web フォントのローカル配置、favicon の同梱、およびハッシュ付きアセット参照の再生成が行われます。また、実ブラウザを起動して各資料の先頭ページをレンダリングし、1200x675 ピクセルの PNG 形式でサムネイル画像を自動生成します S07。

生成されたアセットのうち、ハッシュが付与された静的ファイルは長期キャッシュの対象となり、HTML ファイルなどはアクセスごとに再検証されます。これらはあらかじめビルドされた静的成果物を用いてオフライン再生を行うことを想定しており、パッケージのインストールやビルドの実行時にはインターネット接続が必要です。また、資料内に埋め込まれた任意の外部 iframe コンテンツを自動で取得してオフライン化する仕組みや、Service Worker を用いた製品レベルのキャッシュ機能は備えていません S07。

Stageのデュアルウィンドウ構成とUI機能

デスクトップ向け発表アプリケーションである Stage は、Tauri 2 と Rust をバックエンドとし、フロントエンドのラッパー部分はプレーンな TypeScript による DOM 操作で実装されています。ラッパー UI 自体には Vue や React などの UI フレームワークを採用しておらず、スライドを表示する iframe 内でのみ Slidev 由来の Vue が動作しています S08。

Stage は起動時に「発表者用（presenter）」と「聴講者用（audience）」の2つのネイティブウィンドウを生成します S08。

ウィンドウ 主な役割と配置要素
発表者ウィンドウ 資料選択セレクトボックス、現在のスライド表示、次ページプレビュー、発表者ノート用 textarea（フォントサイズ 12〜28px 調整、保存ボタン）、ディスプレイ選択、フルスクリーン切り替え、ディスプレイ適用、ウィンドウ入れ替え（window swap）、スライド送り・戻しボタン、ブラックアウトボタン、経過タイマー表示およびリセットボタンを備えます。
聴講者ウィンドウ 聴講者向けのスライド表示を中心とします。GUI 上に操作パネル自体を配置しないのではなく、CSS によって操作用パネルを非表示にする実装となっています。

キーボードによる操作体系は以下の通り割り当てられています S08。

  • スライドを進める: Right, Down, Space, Enter, PageDown
  • スライドを戻す: Left, Up, Backspace, PageUp
  • 画面ブラックアウトの切り替え: B, b, .

キー操作の処理では、キーの長押しによる連続入力（repeat）や、Ctrl、Meta、Alt キーが同時に押下されている入力は無視されます（Shift キーは除外されておらず、組み合わせとして受け付けられます）。キー入力の受付は発表者ウィンドウに限定されておらず、両方のウィンドウが入力元として機能します。また、ノート用の textarea を編集中はスライド送りのキー入力が無効化されます。次ページプレビュー領域に対する直接のクリック操作などは行えません S08。

なお、現在の Stage にはファイルダイアログから任意のファイルを開く機能や、URL を直接入力する GUI は存在しません。表示する資料の設定は、起動前に実行するスクリプトによってあらかじめ設定されます S08。

Rustコアによるセッション状態管理とウィンドウ間通信

プレゼンテーションの進行状態は、Rust で書かれたコントローラーが一元的に「正本」として保持・管理します S09。

管理されるセッション状態（Session 構造体）には以下のフィールドが含まれます S09。

  • deck_id: 現在選択されているスライド資料の識別子
  • revision: 対象資料の改訂ハッシュ値
  • page: 現在表示されているページ番号
  • click_index: ページ内でのクリックステップ番号
  • blackout: 画面のブラックアウト状態を示す真偽値
  • session_revision: 状態変更ごとにインクリメントされる変更カウンター
  • timer: タイマーの経過時間（elapsed_ms）と計測開始時刻（started_at）

コントローラーに対して発行できる操作（Action）は、next（進む）、previous（戻る）、toggleBlackout（ブラックアウト切り替え）、selectDeck（資料選択）、toggleTimer（タイマー開始・停止）、resetTimer（タイマーリセット）です。ページ内に複数のクリック要素が存在する場合、進む操作ではクリックを順次消化してから次ページへ進み、戻る操作では同一ページ内のクリックを順次戻してから前のページの最後のクリック状態へと戻ります S09。

資料選択（selectDeck）を実行すると、ページ番号は 1、クリック番号は 0、ブラックアウトは解除（false）に初期化されますが、タイマーの状態はリセットされず維持されます。アクションの入力元（source）は presenter または audience として区別され、source ごとに管理されるシーケンス番号によって重複した要求を破棄します。ノート編集中フラグが有効な間の操作要求は無視され、実際の状態変更が発生した時のみ session_revision が増加します S09。

Tauri のバックエンドプロセス（main.rs）では、フロントエンドから呼ばれる transition コマンドを受け取った際、呼び出し元ウィンドウの実際のラベルに基づいて source を上書きします。内部の Mutex でセッション状態を更新し、更新結果の session イベントを両方のラッパーウィンドウへ配信します S10。

ウィンドウごとのコマンド実行権限は分離されています S10。

  • 両ウィンドウで実行可能: 現在状態の取得（snapshot）、状態遷移要求（transition）
  • 発表者ウィンドウ専用: ノート読み込み（read_notes）、ノート保存（save_notes）、ディスプレイ一覧取得（displays）、聴講者ディスプレイ指定（audience_display）、ウィンドウ入れ替え（swap_windows）

これらに加えて、自動テストや検証を目的とした画面キャプチャ用（capture）などの QA 向けコマンドが別途実装されています S10。

フレーム制御とプロトコルブリッジの契約

各ウィンドウ内でのスライド表示は、TypeScript で記述された frame-controller.ts が iframe を操作し、Slidev 側に読み込まれる deck-bridge.ts と協調して行われます S11。

同一資料内でのページ送りやクリック進行の際は、iframe 全体を再読み込みすることなく、postMessage を介して Slidev 側の Vue Router を直接操作して表示を更新します。異なる資料への切り替えを行う場合は、裏側に配置された待機用の予備 frame で新しい資料のロードを開始し、描画完了（rendered）通知を確認した後に表示中の frame と入れ替えます。この仕組みにより、1つのビューポート（表示領域）あたりで保持される frame 数は active と standby を合わせて最大2枚となります（これはビューポートごとの制限であり、発表者画面のプレビュー表示用にも独立した別の frame-controller が動作しています） S11。

親ウィンドウと iframe 間の postMessage 通信では、なりすましや古いイベントの適用を防ぐため、以下の項目を照合します S11。

  • event.origin の確認
  • event.source === iframe.contentWindow による送信元ウィンドウインスタンスの照合
  • 各フレームに払い出された mount token および document token
  • 対象の資料 ID（deck）、ページ番号（page）、クリック番号（click）
  • コントローラー側の sessionRevision

照合に失敗したメッセージや古いバージョンの応答は破棄されます。また、フレームからの応答待機が15秒を超えた場合はタイムアウトエラーとして処理されます S11。

スライド内のブリッジ機能は、親ウィンドウが iframe の URL クエリに nativeProtocol=1 を付与してロードすることで有効化されます。ブリッジが有効化された controlled frame の内部では、他のタブとの BroadcastChannel による同期や、意図しない二重操作が抑制されます。一方、利用者が通常の Web ブラウザでスライド URL を直接開いた場合には、通常の Slidev として標準的なキー操作や同期機能が維持されます S11。

ローカル実行時のノート編集と整合性管理

ローカル環境で Stage を実行する場合、事前に prepare.mjs スクリプトを実行して必要なアセットを整えます S12。

prepare.mjs は Hub のマニフェストを読み込み、対応しているスライド資料、クリック数、ソース情報を検証した上で、静的ファイルを apps/stage/artifacts/site へコピーします。同時に、非公開の設定ファイルである local-config.json を生成し、ノートのファイルマッピング、ソースのハッシュ値、および許可されたソースディレクトリのルートパス（approvedSourceRoot）を記録します S12。

Stage 上での発表者ノート編集機能は、各スライドページの末尾に既存の HTML コメント（<!-- ... -->）として記載されているノート部分のみを対象としています。汎用的な Markdown エディタとしての編集機能は持っていません。ノートを保存する際は、対象ファイルが approvedSourceRoot 配下に存在することを確認し、外部プロセスによる予期せぬファイル変更がないか、および既存の revision が一致しているかを検証した上で、アトミック（原子的）にファイルを上書き保存します S12。

スライドの構文処理においては、シンプルな v-click 指定のみに対応しています。v-after などの複雑なクリック指定を含むスライド資料は、prepare スクリプトの実行時点でエラーとなり拒否されます。また、資料 ID には ASCII 文字のみが許可されます。なお、ローカルの prepare 処理における ID 文字制約と、リモート接続時の検出処理における制約は完全には同一ではないため、システム全体を横断する共通の保証とはなっていません S12。

発表者がノートを編集したまま未保存の状態でスライドを移動しようとした場合、発表者自身の操作による移動はブラックアウト切り替えを除いてブロックされます。ただし、聴講者ウィンドウなど他方からの入力によってページが移動した場合は、ページごとの編集内容がメモリ内に下書きとして一時保持されます（この下書きはアプリケーション終了時に破棄されます）。なお、スライド本文自体の変更を Stage に反映させるためには、ノートのコメント書き戻しとは異なり、Hub の再ビルド、prepare.mjs の再実行、および Stage アプリケーションの再起動が必要です S12。

リモート接続・認証プロキシとサイドカーノート

Stage は、ローカルに配置された静的ファイルだけでなく、リモートサーバー上で配信されているスライド資料への接続にも対応しています。接続時には connect.mjs スクリプトを使用して接続先の設定を行います S13。

接続対象として指定できる URL は、HTTPS のルートオリジン、またはローカル開発用の HTTP ループバックアドレス（localhost, 127.0.0.1, [::1]）に限定されます。URL にサブパス、クエリパラメータ、あるいは認証情報（ユーザー名やパスワード）が含まれている場合は接続が拒否されます。スクリプトはリモートオリジンの /native-player.json を取得して接続の可否を検証します。マニフェスト取得処理には最大 1MiB のデータサイズ制限と 10 秒のタイムアウトが設定されており、HTTP リダイレクトは遮断されます。リモート先に専用マニフェストとブリッジスクリプトが正しく配備されていることが前提となるため、任意の Slidev サイトをそのまま開くことはできません S13。

リモート資料へのアクセスにおいて認証が不要な場合は、Stage の iframe から直接リモートサーバーへ接続します。一方、アクセス制限が課されている場合は、ローカルに保存された private headers JSON ファイルの内容を参照し、Node 製のコネクターおよび Rust の同一オリジン GET/HEAD ループバックプロキシを経由して必要な認証ヘッダーを付与します。このプロキシ構成により、認証トークンが iframe 内で動作するクライアント側 JavaScript に渡されるのを防止しています S13。

認証ヘッダーの管理は、パーミッション 0600 に設定されたローカルの平文 JSON ファイルを直接読み出す仕様となっています。OS のキーチェーンとの連携、OAuth ログイン画面、SSO トークンの自動リフレッシュなどの GUI 機構は実装されていません。また、実際の Cloudflare Access 環境を用いた接続検証は未実施の状態です S13。

リモート接続時の発表者ノートは、ローカル実行時の Markdown ファイル直接書き戻しとは異なる方式で管理されます。ノート内容はリモートサーバーへ送信されず、接続先となる元のオリジン、資料 ID、ページ番号の組み合わせごとに、Tauri の app_data_dir()/remote-notes ディレクトリ配下へサイドカーファイルとしてローカル保存されます（apps/stage/core/src/sidecar_notes.rs） S13。スライドのソース改訂（source revision）とノートの改訂（notes revision）は独立して追跡されるため、リモート側でスライド本文が更新された場合でもローカルのノートが上書き消去されることはなく、画面上に source_changed の通知が表示されます S13。

リポジトリ構成と責務の境界

現在のコードベースは、ネイティブ発表アプリケーションである Stage、静的ライブラリ生成を担う Hub、両者の通信や検出契約をまとめた protocol、および動的配信を検証する Workers 実験コードで構成されています。

リポジトリの主要なディレクトリ配置は以下のとおりです。

slidev-stage-hub/
├── apps/
│   └── stage/
│       ├── artifacts/
│       ├── core/
│       │   └── src/

Workers実験における動的コンパイルとストレージ

packages/hub/bundle-sharing/experiments/workers は、静的ビルドを行う Hub とは独立して開発されている実験実装です S17。

実行モデルとランタイム構造

本実験では、Node 環境であらかじめ固定テーマ、Slidev ランタイム、コンポーネントおよびレイアウトのレジストリをビルドしておきます S17。実行時（workerd 環境）では、受信した Markdown を Vue ESM、スコープ付き CSS、UnoCSS スタイルへと動的にコンパイルし、ブラウザ側にはランタイム専用（runtime-only）の Vue を配信してスライドを再生します S17。ブラウザ内部でコンパイルを行う構成や、Rust 製コンパイラを採用した構成ではありません S17。

ランタイムの情報は runtime-manifest に保持され、プロファイルダイジェストやブラウザ向けハッシュ値が記録されます S17。固定ランタイムを使用しているため、テーマ定義の変更を反映するにはランタイム自体の再ビルドが必要です S17。

また、この実験環境における一覧画面は runtime/catalog.ts が提供する簡易な DOM 生成によるものであり、Hub の Home.vue とは異なります S17。native-player.json の出力や Stage の deck-bridge との統合は行われておらず、スライドへのアクセス URL も /id/1?revision=... という形式であり、Stage が想定する契約とは直接一致していません S17。

データフローと世代管理

Markdown の登録からストレージ保存、世代管理までのデータフローは以下のようになっています S18。

  1. クライアントが HTTP POST 経由で Markdown と関連アセットを送信します S18。
  2. Durable Objects 上の SQLite（DeckVersions）で新しい世代（generation）を発行します S18。
  3. サーバー側（workerd）で動的コンパイルを実行します（既存リビジョンが存在する場合は再利用されます） S18。
  4. 単一の R2 バケット内において、変換元ソースを非公開プレフィックス private/ に、生成された不変な JS、CSS、アセット、マニフェストを releases/ プレフィックスに保存します。なお、releases/ 内に index.html は出力されません S18。
  5. Durable Objects でコミット処理を行い、新しい世代のコンパイル結果のみが current リビジョンを更新します。処理に時間がかかった過去の古いコンパイル結果が最新リビジョンを巻き戻すことはありません S18。
  6. コミット成功後、同バケットの index/ プレフィックス配下に登録一覧を更新します S18。

過去のリビジョンを指定してスライドを参照することは可能ですが、ロールバックを行うための UI や API は実装されていません S18。また、R2 への直接ファイル配置を検知して Queue 経由で自動的にコンパイルを行う仕組みはなく、HTTP POST エンドポイントを経由した処理のみが存在します S18。

Hub は複数のスライドを束ねて静的な Web サイトとして生成する基盤です S20。標準的な構成で Hub をビルドし、ローカル環境で配信確認を行う手順は以下のとおりです S20。

pnpm build:hub

pnpm build:hub を実行すると、生成物は packages/hub/artifacts/module-graph-offline/site に出力されます S20。続く pnpm dev:hub は、この出力先ディレクトリを静的ファイルサーバーで配信し、ブラウザから http://127.0.0.1:4174 にアクセスして閲覧可能にします S20。ここで注意が必要な点として、pnpm dev:hub はすでに生成された静的ファイルを配信する仕組みであり、開発サーバーのようなファイルの変更監視やホットモジュールリロード（HMR）に伴う自動再ビルド機能は備えていません S20。スライドの変更を反映するには、再度ビルドを実行する必要があります S20。

  1. SLIDEV_THEME_PATH
  2. SLIDEV_LAB_THEME
  3. SLIDEV_THEME_DIR
  4. ワークスペースの公式デフォルト

Stage のビルドと実行には、Node.js に加えてホスト側の SDK が必要です。現在の Linux 開発経路においては、Rust ツールチェーンとともに GTK および WebKitGTK の開発用ライブラリが要求されます S20。これらは現時点の Linux 環境における実行要件であり、将来の全 OS に向けた一般条件として固定されたものではありません S20。

pnpm stage の実体はリポジトリ内の run.sh を呼び出すスクリプトです。このシェルスクリプトの内部では、カレントディレクトリを apps/stage に移動したうえで、以下のコマンドが並列度 2 で実行されます S20。

cargo run --locked -p slidev-native-poc --features desktop

リポジトリルートから直接 cargo run を実行することは想定されておらず、内部スクリプトを経由した呼び出しが前提となっています S20。また、apps/stage/README.md には、環境に応じた任意の SDK 展開手順や、特定の Linux デスクトップ環境で AT-SPI による問題を回避するための NO_AT_BRIDGE=1 という環境変数の指定が記載されています S20。これらは特定環境向けのワークアラウンドであり、一般的な必須要件やアクセシビリティ対応の保証を意味するものではありません S20。現状のビルドプロセスには Node.js が介在しますが、将来的に配布されるバイナリの一般利用者にまで Node.js の導入を必須とする仕様が確定しているわけではありません S20。

Stage はローカルのビルド成果物だけでなく、ネットワーク上でホストされているリモートの Hub に接続してスライドを表示する接続スクリプトも備えています S20。

node apps/stage/scripts/connect.mjs https://slides.example.com
pnpm stage

この接続機能は指定されたオリジンのルートに対して接続を行うものであり、対象サーバー側に対応する成果物が配置されている必要があります S20。なお、すでにローカルで起動している Hub（http://127.0.0.1:4174）を接続先として指定することも可能です S20。connect.mjs スクリプト自体は接続先設定を更新するのみで Stage アプリ本体は起動しないため、設定後に改めて pnpm stage を実行します S20。ローカルの静的ファイル参照に戻す場合は、再度 pnpm stage:prepare を実行してアプリを再起動します S20。
