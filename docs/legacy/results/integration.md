# 共有バンドルとネイティブアプリの統合検証結果

## 概要と判定

本検証では、Slidevで作成された複数スライド資料の共有バンドル化と、TauriおよびWebKitGTKを用いたネイティブ実行環境の統合を評価しました。

**判定**: 検証機上での共有バンドル化およびネイティブ統合の概念実証（PoC）は成立しました（下記の制約条件付き）。全OS対応、物理的な2画面環境への対応、および一般配布向け製品としての完成を示すものではなく、未検証の項目は残課題としてTODOに残します。

## モジュール共有とビルド比較

### 課題と採用方式
Slidev 53.0.0およびローカルの既存固定テーマ（テーマソースの変更がないことをビルド前後のハッシュ値で確認済）を用い、それぞれ3ページで構成される4つの独立資料を検証対象としました。これらを個別にビルドすると重複リソースによって容量が肥大化する課題がありました。

代替案として検討したハードリンク方式は、inodeの論理サイズが11.56%削減されたにとどまり、URLごとの転送量は変わらないため主方式としては不採用としました。また、初期に検討したトップレベルAwait（TLA）方式は、Chromiumでは動作したもののWebKit環境下で3ページ目に停止したため不採用としました（厳密な根本原因は未確定）。

このため、各資料の設定やメタデータ（`configs/metadata`）を先行して読み込み、その後に標準クライアントを起動する同期エクスポート方式（同期ブートストラップ構成）の共有モジュールグラフを採用し、WebKitでの停止問題を解消しました。資料間の遷移は通常の文書ナビゲーションとし、ブラウザの共有HTTPキャッシュを活用する設計です。

### ビルド容量の比較
個別ビルドと共有モジュールグラフ版の成果物比較は以下のとおりです。

| 構成 | ファイル数 | 合計サイズ（raw） | gzip合計（参考値）* | raw削減率 |
| :--- | :--- | :--- | :--- | :--- |
| 個別ビルド（4資料） | 760 | 30,287,165 bytes | 11,445,751 bytes | 基準 |
| 共有モジュールグラフ版 | 227 | 7,626,672 bytes | 2,888,725 bytes | 74.82% 削減 |

\* 注: gzip値は各ファイルを既定設定で個別に圧縮（`gzipSync`）した合算値であり、ネットワークの実転送量を示すものではありません。

### 転送量と描画品質の検証
同一オリジンでのサブリソース転送量（HTMLおよび外部フォントを除く）を測定したところ、個別ビルドでは2資料目の遷移時に3,499,578 bytesを要したのに対し、共有版では初回資料の3,502,641 bytes取得後、2資料目の転送量は16,176 bytesに抑制されました。次資料への遷移時には57リソースのキャッシュが再利用され、他資料専用チャンクの不要な読み込みは0件でした。

表示精度の検証では、基準版と共有版のスクリーンショット比較（12枚）でピクセル完全一致を確認しました。Chromium環境での4資料テスト（画像、CSS、クリック操作、再読み込み、タブ切り替え、カタログ表示、戻る・進む）をすべて通過しています。なお、基準版では機能アサーションを通過したものの、相対パス画像のプリロード起因による404エラーが18件発生し厳格なネットワーク検証（strict network gate）で不合格となっていましたが、共有アダプタの実装により解消しました。

## オフライン化とネイティブアプリの動作検証

### オフラインスナップショット
共有出力にフォントおよびファビコンを同梱し、オフライン環境用の最終スナップショットを作成しました。
- 成果物構成: 475ファイル、raw 13,853,919 bytes、gzip 8,595,838 bytes
- 外部HTTPリクエスト遮断試験（OS側のネットワーク設定は変更せず実施）において、4資料すべてで外部アクセス試行（attempt）0件を確認し合格しました。

なお、フォントファイル数はGoogleエンドポイントの応答に依存するため可変であり、今回の取得では245ファイルでした（以前の取得時は126ファイル）。そのため、記載の値（475ファイル、raw 13,853,919 bytes、gzip 8,595,838 bytes）は最終スナップショット限定のものであり、再取得時に容量が変動する可能性があります。視覚比較においては、基準版と通常共有版が12枚すべてでピクセル完全一致した一方、最終オフラインスナップショットは文字周辺の微差により0/12枚のピクセル一致にとどまりましたが、目視で内容、レイアウト、色の一致を確認しています。また、既存のハッシュ付きファイル名を維持したままCSSやJSの内容に含まれる参照URLを後処理で書き換えているため、公開環境で使用する場合はハッシュ値の再生成が必要です（今回はローカル利用に限定）。

### ネイティブアプリ実行（Tauri 2.12.1 / WebKitGTK 2.52.6）
同一のオフラインスナップショットをネイティブ環境で独立再実行し、18件のアサーションおよびRust側の6テストをすべて通過しました。
- 発表者用と聴衆用の2ウィンドウ構成において、Rust側をページおよびクリック状態の正本として管理。
- 双方向のキーボード操作、発表者ノートの保存、マッピングの永続化と再オープン、外部競合の拒否、下書き保護、プレビュー側の操作禁止、タイマー、ブラックアウト、スライド（deck）切り替えが正常に動作。
- 発表者ノート保存の挙動はGitの差分（no-index）で証跡を確認し、試験後に元のソースコードと一致することを確認済。

## 制約事項と残課題

PoC成立の前提となる条件および未検証の項目は以下のとおりであり、TODOに残しています。

1. **実行環境と起動条件**:
   - AT-SPIクラッシュを当該プロセス限定で回避するため、起動時に環境変数 `NO_AT_BRIDGE=1` の付与が必要です（アクセシビリティ要件は未合格）。
   - 検証機で検出されたモニタは1台のみです。物理2画面環境、高DPIディスプレイ、ディスプレイの抜き差し、およびWindows環境での動作は未検証です。
   - ウィンドウ配置や全画面化APIが受理されることは確認していますが、物理ディスプレイ間を移動したことの証明にはなりません。
2. **描画とシステム連携**:
   - 一部の条件で聴衆用WebViewのスクリーンショット画像が黒くなる事象が発生します（発表者側の描画および聴衆側のDOM同期自体は確認済であり、実ディスプレイ自体が黒くなる現象と断定したものではありません）。
   - 画面スリープを抑制するWake Lock APIは拒絶（denied）されており、OSスリープ抑止機能は未確認です。
3. **データ更新処理と運用**:
   - 発表者ノートの保存は、既存スライド末尾に存在するHTMLコメントの編集のみに対応しており、コメントの新規追加には対応していません。
   - 外部編集の最終チェックからファイルのリネーム処理までの間に、競合状態（race condition）が発生する余地が残っています。
   - Cloudflareへのデプロイ公開、リポジトリへのプッシュ、およびOS側の設定変更は行っていません。

## 再現手順

リポジトリルートにて以下のコマンドを実行します。

```bash
# 共有バンドルのビルド
node bundle-sharing/experiments/module-graph/build.mjs

# オフラインリソースの準備と確認サーバーの起動
node scripts/prepare-offline.mjs
node scripts/serve.mjs artifacts/module-graph-offline/site 4174

# ネイティブ検証（SDKローカル展開・ビルド・準備済みの前提。詳細は ../native-app/README.md を参照）
NO_AT_BRIDGE=1 python3 native-app/scripts/verify.py
```
