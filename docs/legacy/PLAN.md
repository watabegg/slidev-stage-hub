# Slidev Lab 実験・実装計画


## 目的と調査済みの環境


### 計画の目的と検証課題

本計画は、複数の Markdown ファイルとして独立管理される Slidev スライド資料群を、単一の固定テーマのもとで効率的に管理・閲覧・発表できる基盤を確立するための概念実証（PoC）計画である。作成日は 2026 年 10 月 8 日であり、後続の実装エージェントが自走して方針を探索・検証できるよう、正本となる計画書（`/home/watabegg/slidev-lab/PLAN.md`）の前提事実と検証項目を整理する。

現状の Slidev の運用では、以下の 3 つの課題が存在する。

1. **ランタイムコードの重複**: 資料ごとに個別のビルドを行うと、スライド表示に必要な共通の実行時コードが資料の数（N 個）だけ重複して出力され、全体の容量が肥大化する。本計画では、共通の実行基盤と資料ごとのコンテンツを分離し、表示に必要なスライド資料（deck）のみを動的に読み込むバンドル共有の仕組みを検討する。
2. **発表操作と画面制御の制約**: 一般的なブラウザ単体による発表では、複数画面への配置、発表者専用画面の表示、キーボード操作の割り当て、およびスライド画面と発表者画面間の状態同期に課題がある。これに対し、ブラウザエンジン自体の自作は行わず、描画基盤として既存の WebView を活用しつつ、ウィンドウ管理、状態管理、発表者ノートの保持を Rust によるネイティブシェルで制御する構成を模索する。現時点では Tauri と WebView の組み合わせを有力な第一候補としているが、Electron などの他方式を必須または採用確定と決めつけることはせず、実測に基づいて判断を行う。
3. **発表者ノートの永続化と Git 管理**: Slidev では各スライド末尾の HTML コメントを正本として扱う。開発サーバー実行時にはファイルへの書き戻し機構が存在するが、静的ビューアから Git リポジトリへノートを保存する運用は確立されていない。静的配信成果物を再利用する環境において、どのような経路でノートを永続化するかを検証する。

本計画の最終的な目標には、一覧閲覧や将来的な Cloudflare での配信、Windows 環境への対応も含まれるが、まずは手元の Ubuntu PC 上で実際に動作させることを最優先とする。また、固定テーマ同梱のコンポーネント、レイアウト、セットアップ処理は維持対象とするが、新規の資料固有コンポーネントや独自テーマの追加は対象外とする。

今回の作業範囲は、新規リポジトリの初期化、2 つの作業ディレクトリ（`bundle-sharing/` および `native-app/`）の作成、全体計画書の策定、および初期コミットの作成までとし、コード実装、画面モックの作成、依存パッケージの導入、外部公開やリモートへの push は実施しない。`PLAN.md` が正本であり、`TODO.md` はタスク一覧から別途抽出され、各ディレクトリの `README.md` や `AGENTS.md` は親プロセスが別途作成する。PoC 段階で UI や全 API を凍結せず、実測に基づいて変更理由を残しながら進める。OS やコンポジタ、既存リポジトリの設定を勝手に変更することは厳禁とする。

## 2つのPoC


本章では、複数資料における配信と描画の効率化を目指す「バンドル共通化」と、安定した発表環境を提供する「ネイティブアプリケーション」の2つの概念実証（PoC）について、目的、技術的課題、検証手順、合格判定基準、および記録方法を定めます。本計画の段階では新規リポジトリの作成、作業ディレクトリの準備、計画策定、初期コミットまでを対象とし、実際の実装、UIモック作成、外部依存の導入、公開作業は行いません。

### バンドル共通化のPoC（bundle-sharing）


#### 目的と基準測定（ベースライン）

複数の独立したSlidev資料において、共通するランタイムコードやテーマアセットの重複を削減し、ネットワーク転送量と保存容量を抑える方式を確立します。
まず比較基準となるベースラインを測定します。ローカルに配置された固定テーマ（`slidev-theme-watabegg`）を用い、4つの独立したMarkdown資料を標準のSlidevで個別にビルドします。この個別ビルドにおける表示とクリック進行の動作を比較基準とします。測定では架空の達成率や削減数値を設定せず、同一環境で以下の実測値を記録して保存します。

- 実行した正確なコマンドとツールのバージョン
- ビルド所要時間
- 生成物の総バイト数（未圧縮rawサイズおよびgzip圧縮後サイズ）
- 生成ファイル数
- 共通コードの重複状況
- 初回アクセス時および2資料目アクセス時のネットワーク転送量

#### 比較検討するアプローチと制約

以下の方式を比較検証します。

1. **同一モジュールグラフによる共通化（第一仮説）**\
   Viteの同一モジュールグラフ内で共有チャンク（shared chunks）を生成し、各資料を遅延読み込みモジュール（lazy modules）として分離する構成です。本計画の第一仮説として検証します。

2. **仮想モジュールアダプターの適用**\
   Slidevの仮想モジュール機構に対するアダプターを実装するか、必要最小限のパッチまたはフォークを適用します。Slidevの内部APIは安定した公開SDKとはみなせないためバージョンを厳密に固定し、実験結果をもとに変更差分が最小となる手法を選びます。

3. **ビルド後成果物からの重複排除（比較用）**\
   標準ビルドの成果物に対してハッシュ解析、CSS集約、参照パス書き換えを行う手法です。単なるファイル集約にとどまらず、資料間に予期せぬ密結合が生じないかを検証するための比較対象とします。

なお、複数のMarkdownを1つに連結して資料の独立性を失わせる案は要件を満たさないため採用しません。また、生のMarkdownを一般的なMarkdownパーサーで描画する手法も、Slidevの既存コンポーネントやレイアウトとの互換性を欠くため対象外とします。

#### 検証用資材と作業ディレクトリ

作業は `bundle-sharing/` ディレクトリ配下の `fixtures/`、`scripts/`、`experiments/`、`results/` で実施します。採用するレンダラーやマニフェストの形式は実験結果を確認した後に定義します。
`fixtures/` には固定テーマの既存コンポーネントを検証するため、以下の要素を含む4つのスライド資料を用意します。

- タイトル、発表者ノート（notes）、クリック進行（`v-click`）
- テーマ固有のレイアウトと代表的な同梱コンポーネント
- 画像、コードブロック、数式、必要に応じたMermaid図解
- 意図的な衝突検証要素（他資料と同名の相対パス画像、競合し得るCSS定義）

#### 合格判定の基準

個別ビルドと比較し、以下の基準をすべて満たした場合に合格と判定します。

- **資料の独立性**: 各Markdown間でタイトル、ページ番号、notes、CSS、アセット、Vueコンポーネントの状態が混線しないこと。
- **表示と動作の一致**: クリック進行を含め、ベースラインの表示結果と一致すること。
- **不要リソースの遮断**: ある資料を閲覧する際、別資料の全体データや不要なアセットをダウンロードしないこと。
- **再利用性の立証**: 生成物解析とネットワーク測定により、共通ランタイムとテーマの再利用が確認できること。
- **容量削減の実効性**: 総容量が個別ビルドと比較して十分に削減されていること。削減が不十分な場合は不採用とし再実験を行います。ネットワーク取得量の改善と保存容量の改善は明確に区別し、同一環境で測定します。

#### 公開URLの設計と将来の配信構成

公開URLのルーティングは、固定IDとパスの対応（`/aaa/aaa1/1` または `/:id/1`）を第一仮説として検証します。一覧表示（directory listing）、直接URLアクセス、リロード、ブラウザの「戻る」「進む」、存在しないパスへのアクセス時の挙動を確認します。
マニフェストはネイティブアプリとの境界が分かる最低限のメタデータ（`id`, `title`, `sourcePath`, `revision`, `entry`, `assets`, `runtimeVersion`）を暫定候補として定義します。
将来の配信基盤としては、Workerスクリプトの容量制限から配信ファイルを分離できるCloudflare Workers Static Assetsを想定しています。ビルドはローカルまたはCIで完結させ、リクエストごとのコンパイルは行いません。Cloudflare R2は大容量アセットなど必要に応じて検討し、初期はデータベースを用いません。なお、現段階ではCloudflareへの実デプロイおよびWindows向けパッケージングは保留とします。

### ネイティブアプリケーションのPoC（native-app）


#### 目的と段階的な手順

ネイティブアプリケーションの目的は、画面配置、発表先ディスプレイの選択、発表者UI、キー操作、画面間同期、発表者ノートの安全なローカル管理を実現することです。ブラウザエンジンは自作せず、Rustを基盤とするTauriとOS標準のWebViewを第一候補として検証します。Electronは必須でも採用済みでもありません。Windows（WebView2）とLinux（WebKitGTK）のエンジン差は今後の検証事項とし、未検証の互換性は保証せず、まずは開発機であるUbuntu環境での確実な動作を目指します。
本検証はバンドル共通化の完了を待たずに独立して着手できます。初期段階では標準Slidevの成果物を用いてWebView描画と2画面同期を早期検証し、後に共通成果物へ統合します。作業ディレクトリは `native-app/`（`src/`, `src-tauri/`, `experiments/`, `results/`）とし、以下の手順で進めます。

1. **前提条件の確認**: 開発機の `pkg-config` や各種ライブラリ、テーマバージョンの整合性を確認します。実装時にTauri現行版の対応環境と依存関係を再確認します。
2. **最小限のWebView描画**: 最小構成のTauri WebViewを起動し、固定テーマが適用されたスライドを描画します。
3. **2ウィンドウの生成**: 聴講者用（audience）と発表者用（presenter）の2つのウィンドウを生成します。
4. **Rustによる状態管理とイベント中継**: Rustプロセスを正本とし、ウィンドウ間の双方向通信を確立します。
5. **成果物の取得・キャッシュ・オフライン化**: ビルド成果物をダウンロードおよびキャッシュし、オフライン動作を確認します。
6. **発表者ノートの永続化**: 編集したノートをローカルのソースファイルへ保存し、Gitで管理します。

#### 状態管理とイベント設計

進行状態はRustプロセスを正本として集中管理します。状態の候補は以下のとおりです。

- `deckID`, `revision`, `page`, `clickIndex`, `blackout`, `timer`, `session revision`

状態遷移は「1入力1遷移」を原則とする双方向コマンドとして実装し、イベント循環による二重ループを防止します。また、以下の調整を行います。

- ノート編集中はページ送りなどのショートカットキーを抑制します。
- Slidev標準の同期機能や、テーマ側で定義されたキー操作（EnterやBackspace）との競合を調整します。
- 発表者画面の次スライドプレビューは読み取り専用とし、プレビュー側の操作で発表状態が進まないようにします。

#### 画面UIとキーボード操作の検証

静的なUIモックは作成せず、検証を通じてUIレイアウトを決定します。以下の操作と表示を検証対象とします。

- **画面制御**: 発表先ディスプレイの選択、全画面表示、聴講者画面と発表者画面の入れ替え
- **表示要素**: 現在および次スライドのプレビュー、発表者ノート（文字サイズ変更機能を含む）、経過タイマー、画面暗転（blackout）
- **キーボード操作**: 矢印キー、スペース、Enter、Backspace、PageUp、PageDownなど、実際の運用と既存動作に合わせた追従性を確認します。

#### Linux・Wayland環境におけるウィンドウ制御

開発機であるUbuntu（Waylandセッション）では、ウィンドウの配置やフォーカスを自由に制御できる保証はありません。そのため以下の実測と対策を行います。

- 現在のセッション上でウィンドウ配置APIの挙動を実測します。
- 自動配置が困難な場合は、手動配置をフォールバック手順とします。
- X11またはXwaylandとの比較は環境が利用可能な場合のみ実施し、OSのセッション設定を勝手に変更してはなりません。
- 画面の接続解除や再接続時の挙動、高DPI（scaleDPI）での表示崩れを確認します。
- 物理的なマルチディスプレイがない場合は、同一画面上に2ウィンドウを並べる暫定検証にとどめ、記録に「実2画面試験は未実施」と明記します。

#### 発表者ノートの永続化と機密保護

発表者ノートは元のMarkdownファイルにおける各スライド末尾のHTMLコメント等でGit管理する運用を前提とします。

- 本PoC段階では、ローカルリポジトリ内のソースマッピングに基づいて保存し、`git diff` で差分を確認した上で通常の `git commit` を行います。自動的な `git push` やクラウド同期は行いません。
- 保存失敗時や編集中に元ファイルが外部変更された場合の扱いを定め、既存の変更を無言で上書き・破棄してはなりません。
- 機密保護として、非公開ノートが公開バンドルや配信リソースに混入することを防ぎます。公開用にはノートを除去した成果物（stripped notes）を生成し、非公開ノートはローカルのプライベートソースでのみ管理する構成を許容します。

#### オフライン動作とセキュリティ方針

ネットワークが不安定な環境でも確実に動作するようオフライン機能を検証します。

- 一貫したリビジョンのマニフェスト、モジュール、CSS、Webフォント、画像をローカルに保存します。iframeなどの外部埋め込みは例外事項として明記します。
- ネットワーク切断状態で、アプリ再起動、資料切り替え、クリック進行、ノートの編集・保存が動作することを確認します。
- TauriのAPI権限は必要最小限に限定し、任意のリモートページに対してファイルシステムやシェル実行などの特権を付与しません。

### 実験記録と自走の進め方


#### 実験結果の記録フォーマット

実装エージェントは承認された範囲で自走し、実験の失敗を許容して客観的な事実を記録します。各実験の結果は `results/<id>.md` に以下の項目を網羅して記述します。

- **仮説（hypothesis）**: 検証する具体的な仮説
- **実行コマンド（exact command）**: 再現可能な完全なコマンド
- **実行環境（env / dependency / theme revision）**: OS、依存パッケージのバージョン、テーマのリビジョン
- **測定結果とエビデンス（results table / evidence / screenshots paths）**: 比較表、ログ、キャプチャ画像のパス
- **失敗内容と考察（failure）**: 発生したエラーや仮説との乖離
- **採否判定（adopt / reject）**: 結果に基づく採用または不採用の明確な判断
- **次の実験（next experiment）**: 結果を受けて次に実施する検証項目

大容量のビルド成果物やスクリーンショットは `.gitignore` 対象（artifacts）に保存し、リポジトリには簡潔な記録Markdownと再現スクリプトのみをコミットします。

#### 成果物管理と初期着手手順

バンドル共通化とネイティブアプリの境界仕様が固まった段階で、共通成果物の契約仕様（artifact contract）を策定して記録します。現段階でRustのクレート分割などを固定しません。
最初に着手すべき具体的な作業は以下の2点です。

1. `bundle-sharing` における標準Slidev個別ビルドの基準測定（baseline）
2. `native-app` における最小構成のTauri WebViewによるスライド描画検証

RustのビルドやJavaScriptの検証は変更範囲に合わせて実行し、`pnpm` スクリプトや `cargo check`、`cargo test` などのコマンドは導入時に実際に作成・確認された名称を記録します。未作成のスクリプトを実行済みとして扱ってはなりません。また、新規リポジトリ外にある既存テーマの未コミット変更を上書き・コミット・破棄したり、OSやコンポジタの設定を無断で変更したりせず、足りないOS依存は調査の上で必要最小限の対応を判断します。

## 引継ぎと検証


### システム連携とライフサイクル設計

本計画の初期段階では、既存のAPIやデータベースの仕様変更は行わない。複数資料の共有バンドル化とネイティブアプリケーションによる描画・同期という中核機能の成立性を早期に確認するため、設計を複雑化させないことを優先する。資料の構成情報を管理するマニフェスト形式や、RustとWebViewの間でやり取りするコマンド体系については、実機上での概念実証（PoC）を進める中で確定させる。画面構成については既存画面を変更せず、資料一覧（catalog）、発表者向け画面（presenter）、聴衆向け画面（audience）の各画面を新規に作成して対応する予定である。ただし、Slidevの描画基盤を再利用する上で、必要最小限のアダプター実装やパッチ適用等の内部調整を検討することは妨げない。

ネイティブアプリケーションにおける画面やプロセスのライフサイクルは、初期化から終了までの状態遷移を把握するための暫定案として、以下の4段階を候補とする。

1. **loading**: アプリケーションの起動およびスライド資産やWebViewの読み込みを行っている状態。
2. **ready**: 必要なリソースの準備が完了し、発表開始の入力を待機している状態。
3. **presenting**: スライド描画とウィンドウ同期が有効化され、実際の発表操作が進行している状態。
4. **ended**: 発表が終了し、リソースの解放や終了処理へ移行した状態。

エラー発生時の回復処理については、PoC段階で複雑な自動復旧機構を作り込むことはせず、状態の検知と再試行を可能とする暫定的な説明にとどめる。まずは正常系の成立性検証に注力し、過剰な例外処理の実装による遅延を防ぐ。

### 段階的展開と初期スコープ

実装の展開にあたっては、手戻りを最小限に抑えるため、検証範囲を段階的に拡大する。
まずローカル環境において、個別のスライド生成と共有バンドルの動作を確認する。次に、開発機であるこのPC（Ubuntu環境）上でバンドル共有とネイティブアプリケーションを統合し、実機での動作を確立する。Windows環境への対応やCloudflare（Workers Static Assetsなど）への配信展開は、このPCでの検証を完了させた後の課題として扱う。
また、バイナリの配布用署名、自動更新機構、外部向け公開パイプラインの構築も後段の工程に回し、初期PoCのスコープから除外する。リポジトリの初回コミットは計画文書（`PLAN.md` など）と各作業ディレクトリの `README.md` による構造保持のみとし、リモートリポジトリ（`git remote`）の設定は行わない。

### 未確定事項と自走の基準

実装を担当するエージェントは、検証結果や設計方針を根本から左右する情報不足が発生した場合を除き、不要なユーザー承認ゲートを設けずに承認済み範囲で自走して作業を進める。現在把握されている未確定事項と、それらに対する初期対応方針は以下のとおりである。

| 項目 | 状態と課題 | 初期対応方針 |
| :--- | :--- | :--- |
| モニタ構成（Topology） | 物理画面の接続状況や配置情報が未確認 | まずRust側でモニタ検出処理を実装する。物理画面が不足する環境では、その制約を記録した上で単一画面または擬似ウィンドウでの限定検証として記録する。 |
| WebKitの実際の互換性 | Linux（WebKitGTK）上でのSlidev機能の動作実績が未確認 | このPC上で実際に描画させ、テーマやレイアウトの互換性を実測して評価する。 |
| 最適なバンドル共有アダプタ | 重複コード削減と独立ルーティングに最適な方式が未選定 | 複数のバンドル方式を候補として比較測定し、ビルド時間やサイズから選定する。 |
| 発表者ノートの公開方針 | 配布資料と発表者専用メモの分離方針 | 原則として非公開（default nonpublic）を前提とし、公開向け成果物には含めない。 |
| Windows環境の対応 | 開発機（Ubuntu）と異なるOSでの動作保証 | 初期検証の対象外とし、後段の独立した検証課題として切り離す。 |

### 完了定義（DoD）と判定ゲート

本PoCの各マイルストーンを完了とみなすには、以下の客観的な判定条件を満たす必要がある。

1. **基準ビルドとの比較評価**: 単独でビルドしたスライド資料および既存テーマ（slidev-theme-watabegg）の表示が正常であることを確認した上で、バンドル共有版との表示およびサイズ比較を実施すること。
2. **バンドル再利用の客観的証拠**: 共通実行コードの重複削減効果について、計測データやビルド出力などの具体的な証拠を伴って評価されていること。
3. **資料間の非混線**: 複数のスライド資料を同時に、または順次切り替えて描画した際、スタイル、状態、アセットが相互に干渉（混線）しないこと。
4. **実機機能の充足**: このPC上で、WebViewによるネイティブ描画、Rustでの状態同期、オフラインでの閲覧、および発表者ノートのローカルGit差分（git diff）管理が正常に動作すること。
5. **画面検証の誠実性**: 実際の2画面表示テストは、物理的に検証可能な環境でのみ実施する。画面が不足して実施できなかった項目は「未実施」として記録し、決して合格扱いにしてはならない。

PoCの過程で不採用となった候補技術については、その理由を記録した上で除外するが、その失敗が別の独立した検証の継続を妨げるものではない。また、実行コマンドの記録においては、現時点で動作が確認できている前提条件（prereq）の実行例と、将来整備される予定のスクリプト群（scripts）とを明確に区別して記載しなければならない。Windows環境やCloudflareへの配信が未検証であっても、このPC上での目標を達成していればマイルストーン完了とみなすが、それを「クロスプラットフォーム対応の完了」と呼称してはならない。
