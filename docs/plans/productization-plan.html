1. 目的と背景

本文書は、Slidev を基盤とする発表・受講環境「Stage」およびスライド配信・集約基盤「Hub」の実装基盤を再設計し、保守性と疎結合性を高める実装計画を策定することを目的とする。対象読者はリポジトリ保守者および実装担当者であり、最終成果物は HTML 形式の実装計画書となる。現時点（2026-10-09）では計画策定段階であり、実装作業には未着手である。対象コードベースは main@0885420 および既存の未コミット差分とし、既存の検証成果や作業途中の差分を破棄せず活用することを前提とする。

本計画において最優先とされる方針は以下の通りである。

  • 実験機能の本体集約: experiments/ 配下に分散していた機能のうち、実用に足る検証済みロジックを正規パッケージへ統合する。
  • 疎結合な構成: 各パッケージ間の責務境界を明確化し、特定の実行環境（Node.js、ブラウザ、Cloudflare Workers、Tauri / Rust）に対する不要な依存を排除する。
  • 機能動作と実用性の担保: 公式 Slidev のデフォルト動作および watabegg 1.2.1 サンプルとの互換性を完全に維持し、無駄のない設計を徹底する。
  • CLI の操作性向上: 設定ファイル、環境変数、コマンド引数の優先順位を整理し、一貫したインターフェイスを提供する。
  • Web フロントエンドの差替え性向上: 配信プラットフォームのフロントエンドについて、ソース、レンダラー、スタイルを安全に差し替え可能とする。
  • 開発基盤の近代化: リポジトリ全体の開発ツールとして Oxlint、Oxfmt、AGENTS 規約を整備し、品質管理を自動化する。
  • UI デザインの優先度分離: アプリケーションおよび Web の画面デザイン刷新は後回しとし、基盤アーキテクチャの確立を先行させる。

本計画のスコープ外（非対象）とする事項は以下の通りである。

  • アプリケーションおよび Web 画面の大幅なデザイン刷新。
  • Slidev の全機能に対する無制限な対応拡大。
  • Cloudflare R2 から Queue への新規自動化パイプラインの構築。
  • SSO（シングルサインオン）認証基盤の刷新。
  • あらゆるオペレーティングシステムに対する網羅的な動作保証。
  • パブリック npm レジストリへの公開、本番クラウド環境への自動デプロイ、コード署名の導入。
  • 既存の slidev-lab および slidev-watabegg に対する変更（禁止事項）。なお、計画実行時においても外部公開の可否は別判断とする。

再設計における完成形の依存方向は、厳格な単方向グラフとして定義する。各パッケージ間の境界は pnpm workspace 依存および package.json の exports フィールドにより制御する。

本計画の策定にあたり、以下の既存ファイルおよび実装内容の精査を完了した。

  • ドキュメントおよび設定: docs/HANDOFF.md, TODO.md, docs/DEVELOPMENT.md, package.json, pnpm-workspace.yaml, .github/workflows/checks.yml, docs/results/portability.json
  • protocol パッケージ: packages/protocol/src/{native-player.mjs,inspect-deck.mjs,deck-bridge.ts,globals.d.ts}, packages/protocol/{package.json,tsconfig.json,scripts/build.mjs}
  • stage アプリケーション: apps/stage/{package.json,tsconfig.json}, apps/stage/scripts/{prepare.mjs,connect.mjs,build-ui.mjs}, apps/stage/src/{app.ts,frame-controller.ts}, apps/stage/src-tauri/src/{main.rs,auth_transport.rs}, apps/stage/core/src/{lib.rs,sidecar_notes.rs}
  • hub パッケージ: packages/hub/bundle-sharing/experiments/module-graph/{build.mjs,profiles.mjs,profile-probe.mjs}, packages/hub/frontend/{Home.vue,home.ts,catalog.ts,navigation.ts}, packages/hub/scripts/{environment.mjs,thumbnails.mjs}
  • workers 実験実装: packages/hub/bundle-sharing/experiments/workers/{worker.mjs,compiler.mjs,build-runtime.mjs,runtime/entry.ts,runtime/routes.ts,runtime/bridge.ts,package.json}

精査の結果、判明した現行実装（AS-IS）の技術的実態は以下の通りである。

  1. protocol の実態: native-player.mjs は fs および path モジュールでソースファイルを読み込み、引数として外部パーサーを受け取る設計となっている。また、inspect-deck.mjs は Node.js の Buffer を直接使用してバイトオフセットを計算している。これらは純粋なワイヤ契約（シリアライズ可能なデータ定義）になっておらず、Node.js ランタイムに依存している。さらに、globals.d.ts には Stage のプライベートな型定義が混在し、ビルド方式も classic script 形式にとどまっている。

  2. Hub の実態: Hub の中核ロジックは packages/hub/bundle-sharing/experiments/module-graph に配置されている。build.mjs は process.env、カレントワーキングディレクトリ（CWD）、リポジトリルートパスへの依存が強い。また、フロントエンド実装が固定されており、Slidev 内部の Vite 処理、文字列パッチ処理、ビルド成果物生成が同一コード内で混在している。一方で、profiles.mjs が備える「Slidev のグローバルキャッシュ汚染を回避するための子プロセス隔離機構」は正常動作に不可欠であるため、新設計でも維持する必要がある。

  3. Web フロントエンドの実態: Home.vue および catalog.ts では、fetch('/catalog.json') のレスポンスに対して単純な型キャストを行っているのみで、スキーマバリデーションが不足している。navigation.ts には CSS スタイル、画面文言、リンク構造が固定化されている。さらに、Workers 側では異なるカタログ実装が独立して存在している。

  4. Stage の実態: Rust core (apps/stage/core) が状態の正本（Single Source of Truth）を保持する一方、Tauri ホスト側 (apps/stage/src-tauri) はウィンドウ管理、OS イベント、ファイルシステム操作、認証処理などの過大な責務を担っている。Node.js 版の prepare.mjs はマニフェスト内の sourcePath を Hub ルート基準で解決する。Tauri ホストはビルド時の CARGO_MANIFEST_DIR に基づくパスに依存して起動する。connect.mjs では、strict root origin チェック、1MiB ペイロード制限、10秒タイムアウト、リダイレクト禁止（no redirect）、認証ファイルパーミッション 0600、設定ファイルのアトミック書き込みが実装済みである。しかし、prepare.mjs によるサイト全体のコピー処理および設定書き込み全体はアトミック化されていない。下書きノート（draft notes）はメモリ上に保持され、リモート sidecar ノートは origin、deck、page の識別子（identity）に基づいて紐付けられている。

  5. Workers の実態: Cloudflare Workers 向けには独立した限定コンパイラが実装され、Cloudflare R2 の releases ストレージと Durable Objects (DO) の generation / current ポインタを用いたバージョン管理が行われている。POST /api/decks/{encoded-id} リクエストで generation を予約し、コンパイル成果物を R2 に保存した上で、新しい generation のみ current ポインタを更新する。既存の /api/catalog は R2 インデックスの単一ページ取得にとどまり、Stage discovery との連携機能が存在しない。runtime/bridge.ts は slideSetup の補助を行うのみで、ネイティブブリッジとしての機能を備えていない。また、コンパイラには 512KiB ペイロード上限および 100 スライド上限があり、コードブロックや数式のプレーンテキスト化に関する警告、Mermaid 記法の拒否処理が実装されている。さらに、型チェック対象から Workers ランタイムが脱落している。

現行実装における各資産の扱いについて、本体への昇格対象と検証資産を以下のように台帳化して整理した。

3. Problem と Solution

既存実装の分析から特定された課題（Problem）と、本再設計計画による解決策（Solution）の対応関係は以下の通りである。

課題分類 既存実装の課題 (Problem) 本計画における解決策 (Solution)
パッケージ構成 主要ロジックが experiments/ 配下に散在し、パッケージ間の依存境界が不明瞭である。 仮 private パッケージ @slidev-stage-hub/{protocol,hub,slidev-adapter,stage-tools,cli} を新設し、依存方向を単方向化する。
プロトコル契約 protocol 内で Node.js 固有 API (fs, Buffer) や Stage 私有型が混在し、ブラウザや Workers で共有できない。 protocol から環境依存コードを排除し、純粋なワイヤ契約、データ型定義、共通バリデータのみに純化する。
Hub ビルド build.mjs が環境変数、CWD、Slidev 内部 Vite 実装に強く依存し、外部からの再利用やテストが困難である。 Slidev 依存処理を slidev-adapter に集約し、Hub 本体は公開 Node API buildHub および設定ファイル経由で宣言的に制御する。
Stage 整合性 prepare.mjs のファイルコピーと設定書き込みが非アトミックであり、ビルド失敗時に不整合状態が残る。 一時作業領域でのビルド検証を経てバージョンディレクトリを確定し、設定ポインタを原子的に切り替える仕組みを導入する。
Workers 連携 Workers 実装が孤立しており、Stage discovery と連携できず、カタログ形式の不一致や型チェック漏れがある。 新設の GET /catalog.json および GET /native-player.json (schemaVersion: 2) を導入し、リビジョン固定再生に対応させる。
品質保証基盤 パッケージ境界の違反を検出する仕組みがなく、コードフォーマットや Lint 規約が一貫していない。 Oxlint、Oxfmt、境界検証スクリプト (scripts/check-boundaries.mjs) を導入し、CI 上で機械的に違反を検知する。

4. 設計判断と代替案

本計画の策定において検討された主要な設計判断と、却下された代替案の比較内容は以下の通りである。

判断1: アーキテクチャ移行のアプローチ

  • 採用方針: 機能単位の段階的抽出（Incremental Extraction）
    • 理由: 既存の動作実績および main@0885420 の未コミット差分を確実に保護し、8つの Step と Gate に基づいて段階的に機能等価性を検証しながら移行できるため。
  • 却下した代替案: 一括書き換え（Big Bang Rewrite）
    • 却下理由: 回帰バグの発生箇所を特定することが極めて困難になり、既存の動作検証資産や未コミットの成果を失うリスクが高いため。

判断2: パッケージ分割と共通化の方針

  • 採用方針: ランタイム単位のパッケージ分離（Runtime-targeted Packages）
    • 理由: Node.js、ブラウザ、Cloudflare Workers、Tauri / Rust の各実行環境では、使用可能な API やリソース制限（Workers の 512KiB 上限など）が大きく異なる。ランタイムごとにパッケージを分離し、exports フィールドで境界を強制することが最も安全であるため。
  • 却下した代替案: 巨大な単一共通コア（Monolithic Core）
    • 却下理由: Node.js 固有のモジュール（fs、path、Buffer 等）が誤ってブラウザや Workers 環境に混入し、バンドルサイズの肥大化やランタイムエラーを引き起こす原因となるため。

判断3: スライドコンパイラの実装方針

  • 採用方針: 静的 Hub と Workers で専用アダプターを分離し、プロトコル契約のみを共有
    • 理由: 静的ビルドにおけるフル機能の Vite / Slidev 処理と、Cloudflare Workers における制限付きオンデマンドコンパイラでは実行モデルが根本的に異なる。共通化すべきは入出力のデータ構造（スキーマおよびバリデータ）であり、コンパイラ本体を無理に統一しない。
  • 却下した代替案: 単一コンパイラへの完全統一
    • 却下理由: Workers の V8 アイソレート環境および厳しいメモリ・CPU 時間制限に対して、重量級の Vite エコシステム全体を適合させることは現実的でなく、保守不能な複雑性を招くため。

判断4: 拡張性とアーキテクチャパターン

  • 採用方針: 明示的な引数（Options）とモジュール exports
    • 理由: コードの追跡性を最大化し、無駄のない最小限の設計を保つため。API は引数オブジェクトで完結させ、依存関係は通常の静的 import / export で表現する。
  • 却下した代替案: 汎用プラグイン機構や DI（依存性注入）コンテナの導入
    • 却下理由: 現在のシステムの規模と要求に対して過剰設計（Over-engineering）であり、デバッグの困難さや設定の複雑化を招くだけで実利が乏しいため。

判断5: TypeScript 化の適用戦略

  • 採用方針: 本番実行ロジックおよび契約境界から優先的に TypeScript 化
    • 理由: 最も型安全性が求められるプロトコル定義、公開 API、コアロジックを優先して型付けし、早期に型チェックの恩恵を得るため。
  • 却下した代替案: 全スクリプトおよび実験コードの一斉 TypeScript 化
    • 却下理由: 一時的な検証用スクリプトや測定ツールの型付けに過大な作業工数を割くことになり、基盤再設計の実装進捗を阻害するため。

Web スライド再生画面 (Workers 配信時) 既存 Workers runtime では ?revision=... によるリビジョン固定（pinRevision）を実装済みだが、Stage discovery や native bridge との連携は未実装。 見た目は Slidev default を維持しつつ、Stage discovery と native bridge の正式統合を行う。 発表中のスライドが別端末から再パブリッシュされても、進行中のセッションが破綻せず、Stage からの連携再生が可能になる。

6. API 仕様の変更

6.1 公開 Node API 計画（新設予定）

公開 Node API は、環境変数やプロセスのグローバル状態に依存せず、引数の options のみで動作を完結させる。エラー発生時は process.exit を呼び出さず、エラーコードを含む型定義された例外（typed error）をスローする。また、進行状況はコールバック関数で通知し、秘密情報（認証トークン等）は戻り値やログに含めない。

  • buildHub(options: HubBuildOptions): Promise<BuildResult>
    • 設定ファイルまたは明示的なオプションを受け取り、Hub の静的サイトをビルドする。
    • プロファイル実行時の Slidev グローバルキャッシュ回避を目的とした子プロセス隔離は、内部実装として隠蔽して実行する。
  • prepareStage(options: StagePrepareOptions): Promise<StageConfigResult>
    • ビルド済みのスライドサイトおよびマニフェスト成果物を検証し、Stage 用に配置・ステージングする。
    • 後述する一時ディレクトリを用いた原子的ライフサイクルを実行する。
  • connectStage(options: StageConnectOptions): Promise<StageConfigResult>
    • 指定された Hub（ローカルまたはリモート）に接続し、設定情報を同期・生成する。

6.2 CLI 計画（新設予定）

CLI コマンドは @slidev-stage-hub/cli パッケージから提供される計画であり、以下のサブコマンド群で構成される。

CLI の共通仕様および規約は以下の通りとする。

  • 全コマンドで --help による実行例を表示可能とする。
  • --json フラグ指定時は、結果情報を単一の JSON オブジェクトとして stdout に出力し、進捗メッセージやログは stderr に出力する。
  • 終了コードは厳格に統一する: 正常終了は 0、入力誤り（引数不正や設定構文エラー）は 2、実行時失敗は 1 とする。
  • エラーオブジェクトには安定した識別文字列 error.code を付与する。
  • 自動化環境向けに --non-interactive フラグをサポートする。
  • 既存の pnpm scripts は、これらの新設 CLI を呼び出す薄い互換ラッパーとして再編する。
  • パラメータ解決の優先順位は「コマンドライン引数 > 設定ファイル > デフォルト値」とする。従来の環境変数は互換ラッパー内でのみ変換し、設定値と衝突した場合は警告を出力する。
  • 入力エラー検出時は、ソースファイルや出力先ディレクトリの内容を一切変更しない。未知の設定キーが検出された場合は即座にエラーとする。

6.3 新設定ファイル slidev-hub.config.json 計画

設定ファイルは schemaVersion: 1 を持ち、Hub の動作を宣言的に規定する。

  • 主要フィールド:
    • schemaVersion: 整数値 1（固定）。
    • sourceRoot: スライドファイル群のルートディレクトリ（相対パスは本設定ファイルの配置場所基準）。
    • outDir: ビルド成果物の出力先ディレクトリ。
    • decks: 対象デッキの定義。省略時は既存のディスカバリ機構を使用し、指定時は明示的エントリリストとして処理。
    • theme: 適用する共通テーマ設定。
    • frontend: フロントエンドのカスタマイズ定義 ({ entry?: string, styles?: string, navigation?: NavigationConfig })。
  • 制約事項:
    • frontend.entry に指定可能なパスは、信頼されたローカルファイルシステム上のビルド入力に限定し、任意のリモート URL 指定は禁止する。
    • Node API においても本設定ファイルと同一のパス正規化ロジックを使用する。
    • 高度な Vite 内部設定の全面的な外部公開は行わない。

6.4 カタログ API 仕様

  • 既存の schemaVersion: 1 ({ categories: Category[], decks: DeckSummary[] }) を維持する。
  • カタログデータの純粋なバリデータ関数を @slidev-stage-hub/protocol に実装する。
  • Workers 環境において、新設エンドポイント GET /catalog.json を提供し、R2 上のデータを既存スキーマへ正規化して返却する（従来の /api/catalog も互換性のため維持）。
  • サムネイル画像が存在しない場合は、既存のデフォルトプレースホルダー画像へフォールバックする。
  • インターフェイス規約として catalogSource.getCatalog({ signal?: AbortSignal }): Promise<CatalogData> を定義し、アダプター createCatalogClient により静的配信と Workers 配信の双方に対応する。
  • カスタムエントリ、CSS、ナビゲーションの差替え動作はテスト用フィクスチャにより検証する。
  • Workers における R2 list cursor 処理は、カーソルを追従して全件取得を行う。ただし、1リクエストあたりの最大処理量を明示的に設定し、上限を超過した場合は安全にエラーを返却する（サイレントなデータ欠落を禁止）。

6.5 ディスカバリ API（Discovery）仕様

  • 静的配信: GET /native-player.json は既存の schemaVersion: 1, protocolVersion: 1 を維持する。
  • Workers 配信: 新設エンドポイント GET /native-player.json は schemaVersion: 2, protocolVersion: 1 を採用する。
    • デッキ定義に id, revision, entry, clickTotals を含め、さらに playback: { kind: 'revision-query', parameter: 'revision' } を付加する。
    • parameter の値にはリテラル文字列 'revision' のみを許可し、任意のクエリパラメータ注入を禁止する。
    • Stage アプリケーションは v1 および v2 の双方を読み取り可能とし、v2 を検出した場合は URLSearchParams を用いて再生 URL に revision を確実に固定し、必要なネイティブフラグを付与する。
    • 旧バージョンの Stage は v2 を検出した場合に明示的に拒否（reject）する。なお、v1 に未知のフィールドを追加する代替案は、現行の Stage connect 実装が未知のフィールドを削除（drop）してしまうため不採用とする。
    • Stage UI および Rust config にも playback 情報を保持し、v1 形式の場合は従来の既定動作を維持する。

6.6 バリデーションおよび通信制約

  • 既存の検証ルールを維持する: canonical ID 形式、strict root origin チェック、エントリパスの完全一致 (/id/1)、クリック総数の u32 範囲、空文字でない revision 文字列。
  • 通信上の安全制限: ペイロードサイズ上限 1MiB、リクエストタイムアウト 10秒、HTTP リダイレクト禁止（no redirect）を維持する。
  • ブラウザブリッジ通信: protocolVersion: 1 を維持し、トークン、オリジン、ソース、リビジョン、ページ番号、クリック数の照合処理を継続する。
  • 現行の ID バリデータ間に存在する挙動差は、既存フィクスチャを確認した上で共通のサポート対象サブセット（supported subset）に正規化する。勝手な全体 ID リネームは行わない。

6.7 Workers コンパイラ契約

  • native metadata は、対応するクリックセマンティクスが完全に証明できるデッキに対してのみ付与する。
  • unsupportedDecks に記録する理由は汎用的な理由文字列（generic reason）に限定し、内部のプライベート Markdown、ファイルパス、発表者ノートの内容は一切露出させない。
  • 過去に生成された既存リリース（R2 releases）は改変しない。native metadata を持たない既存デッキは Web 再生可能であるが Stage 未対応として扱う。
  • コンパイラ契約のダイジェスト（compiler contract digest）を更新することにより、再パブリッシュ時に確実に新しい revision を発行させ、既存キャッシュとの意図しない衝突を防止する。

7. データモデル・DB 変更

本計画におけるデータ永続化層の設計方針は、既存のスキーマおよびストレージ構造を尊重し、不要なマイグレーションを発生させないことである。

7.1 ストレージおよび永続化構造の維持

  • Cloudflare Durable Objects (DO) SQLite: 既存のテーブル構造、generation カウンタ、current ポインタ管理テーブルをそのまま維持する。リレーショナルスキーマの変更は発生しないため、DB マイグレーション作業および ER 図の作成は不要である。
  • Cloudflare R2: 既存のキー構造である private/（中間データ）、releases/（コンパイル済み成果物）、index（公開インデックス）プレフィックスを維持する。
  • 発表者ノート（Sidecar Notes）: 既存のリモート sidecar 形式を維持する。

7.2 設定・マニフェストの加法的契約

  • 新設する JSON 設定およびマニフェストは原則として加法的契約（additive contract）とする。ただし Discovery については、旧 Stage が明示的に拒否できるよう新設の schemaVersion2 を導入して v1 読み取りを維持し、他の設定には旧フォーマット読み取り用のアダプタを提供する。
  • ソースコードとビルド成果物のマッピング情報は非公開のビルド受領書（private build receipt）にのみ記録し、一般に公開される catalog.json や native-player.json からは絶対パスや発表者ノートなどの機密情報を完全に排除する。

7.3 Stage ローカルデータ管理

  • 設定ファイルの配置: CLI から明示的に --config オプションで指定可能とする。指定がない場合のデフォルトパスは、プロジェクトローカルの .slidev-stage/local-config.json とする。
  • 発表者ノートの永続化: ローカルでのノートデータは、OS 固有のアプリケーションデータ領域（app_data）に保存する。旧設定形式を読み込むためのアダプター層を用意する。
  • Rust アプリケーション識別子: 既存の識別子 local.slidev.lab を維持する。識別子の変更に伴ってノートの保存先ディレクトリが暗黙的に変更される事故を防止する。

8. ステータス・ライフサイクル変更

8.1 状態モデルの前提

Stage の Rust core (apps/stage/core) に実装されている既存の状態集合およびステートマシンは変更せず、そのまま状態の正本として維持する。

8.2 Stage prepare の原子的ライフサイクル（新設予定）

現行のファイルコピーおよび設定書き込みにおける非アトミック性を解消するため、以下の厳格なライフサイクルを導入する。

  1. 一時作業領域へのビルド: 専用の一時ディレクトリ（temp staging）に対してビルド済みスライドサイトの検証および配置を実行する。
  2. 成果物の整合性検証: 生成されたファイル群の存在、マニフェストの構文、必須アセットの欠損有無を静的に検証する。
  3. バージョンディレクトリへの確定配置: 検証が完全に成功した場合に限り、バージョン番号を付与した正式ディレクトリ（version dir）へ成果物を確定配置する。
  4. 設定ポインタの原子的切り替え: 設定ファイル内の参照先ポインタを新しいバージョンディレクトリへアトミックに書き換える。
  5. 失敗時のフォールバック処理: ビルドまたは検証のいずれかの段階でエラーが発生した場合は、即座に処理を中断して一時作業領域を破棄し、直前の既存設定と成果物ディレクトリをそのまま有効（Active）として維持する。
  6. 世代保持クリーンアップ: ポインタ切り替えの成功後にクリーンアップ処理を実行し、現在のアクティブ世代（Active）と直前の1世代（Previous）の合計2世代のみを保持し、それ以前の古い世代の成果物を削除する。

8.3 Workers publish のライフサイクルとセッション分離

  • generation の順序保証: 既存の順序管理を維持する。パブリッシュ要求時に DO 上で generation 番号を予約し、R2 への成果物保存が完了した段階で、予約した generation が最新である場合のみ current ポインタに昇格させる。
  • リビジョン固定によるセッション保護: あるスライドデッキに対して新しいバージョン（B）が再パブリッシュされた場合でも、既に接続・受講中の Stage セッション（バージョン A）は、URL クエリパラメータ ?revision=A により固定された過去リビジョンの R2 成果物を参照し続ける。これにより、発表中のスライドが突然更新されてセッションが切断される事態を防止する。
  • 新バージョンの反映タイミング: Stage 側で明示的に stage connect を再実行したタイミングで最新の native-player.json (v2) が取得され、新バージョン B への切り替えが行われる。

8.4 変更しないライフサイクル

Stage におけるプレゼンター画面とディスプレイ画面間の Tauri invoke / event および iframe postMessage による内部フレーム同期ライフサイクル、token / origin / source / revision / page / click 照合手順は、既存の設計および役割分担を維持する。

Step 2: protocol/Slidev境界

目的

通信規約を担う protocol のランタイム契約から環境依存モジュール（fs、path、Buffer などの Node.js 組み込み API）や Slidev 固有処理を完全に排除し、純粋な TypeScript による契約（contracts）として独立させる。同時に、ファイルシステム操作や Slidev 内部 API への依存処理を新設予定の slidev-adapter に集約し、ブラウザおよび Workers で利用可能な境界を明確に分離すること（Gate G2）を目的とする。現時点では計画段階であり、既存の動作要件を破壊せずに移行する。

実装手順

  1. ワイヤ規約・バリデータとブリッジの純粋 TypeScript 化: Catalog、Discovery、Bridge などの通信電文規約およびバリデータを純粋な TypeScript（pure TS）として再実装し、packages/protocol/src/globals.d.ts に混在していた Stage 私有型を apps/stage/src/types へ移動して分離する計画である。ブラウザ（browser）および Workers（worker）環境のランタイムで動作可能とするため、fs、path、Buffer などの Node.js 組み込みモジュールへの依存を protocol のランタイム契約から排除し、純粋な wire 契約のみを protocol に残す。最新の ESM 契約エントリと、従来の互換性を維持する classic bridge は、ビルドエントリを明確に分離して出力する構成とする。
  2. Slidev 依存およびファイルシステム処理の Node アダプタ集約: ファイルシステム操作、Slidev パーサー呼び出し、バイトオフセット（byte offset）計算の処理を新設予定の packages/slidev-adapter（Node.js 前提）へ移設する計画である。Slidev の内部 API や文字列パッチ（string patch）処理を slidev-adapter 内に集約し、Slidev バージョン 52 および 53 のフィクスチャに対してシグネチャ不整合（signature mismatch）を検知した場合は明示的なエラーを送出するよう実装する。日本語などのマルチバイト文字や CRLF 改行コードにおけるバイトオフセットの正確性を検証し、ソース上書き（source overwrite）契約の整合性を維持する。
  3. workspace exports への移行と Rust 整合性検証: 各パッケージ間の参照を workspace exports 経由に切り替える。なお、旧 protocol exports を非推奨ラッパーとする方針は adapter との循環参照を招くため採用せず、Step 2 内で全内部 caller を新 exports へ同時移行した上で旧 Node 専用 protocol exports を削除する（既存の pnpm entry および wire v1 互換性は維持する）。Rust 側の serde 構造体と TypeScript 側のバリデータとの整合性は、共通の JSON fixtures を用いて valid / invalid 両系統のパリティ（等価性）を検証するテストにより担保する。大掛かりなコード自動生成基盤は導入しない。

11. テスト計画

11.1 テスト方針と目的

本再設計計画におけるテストの目的は、内部構造の変更やモジュール再配置の影響を受けず、システム境界における契約と外部から観測可能な振る舞いを保証することにある。内部クラスやプライベート関数の実装詳細をそのままなぞるテスト（Implementation Mirror）を作成すると、責務の分離やアダプタ抽出のたびにテストコードの修正が必要となり、リファクタリングの継続性を著しく損なう問題が生じる。

この課題を解決するため、本計画では各パッケージの入出力境界、例外ハンドリング、および非同期メッセージの整合性に焦点を当てた振る舞い検証を中心とする。RustコアとTypeScript層のデータ交換契約、ファイルパス解決における文字コードや特殊文字の処理、CLIインターフェースの終了ステータス、配信ランタイムの同時実行制御など、外部契約としての正しさを網羅的に検証する設計を採用する。

12.1 セキュリティ保護要件

基盤の再設計作業において、既存のコードベースが備えているセキュリティガードをすべて維持することを必須要件とする。アーキテクチャの変更を理由とする防御策の緩和や省略は認めない。

  1. 秘密情報のアクセス権限: トークンや認証情報を保持するローカル設定ファイルは、ファイルパーミッションを厳格に 0600（所有者のみ読み書き可能）に設定し、同一ホスト上の他ユーザーからの参照を制限する。
  2. コンテンツの非公開保護: 非公開（private）Markdown 原文、実パス、発表者ノートのすべてを公開用のカタログや Discovery 成果物に含めず外部へ露出させない（公開スライドの閲覧表示仕様は継続し、非公開ソース配信用の新規 API 追加は行わない）。
  3. 通信保護と入力検証: 通信はHTTPSオリジンを基本とし、配信ルートの適切な制限、不正なオープンリダイレクトの防止を徹底する。また、認証ヘッダーやシークレット情報がサーバーログへ平文で出力されることを禁止する。
  4. カスタムフロントエンドの信頼境界: ユーザーが持ち込むカスタムフロントエンドコードは、ローカル環境で明示的に信頼されたコード（Trusted Local Code）として扱う。不要な過剰サンドボックス化による開発体験の悪化は避けるが、不特定多数の外部スクリプトの無制限な読み込みは許容しない。
  5. 更新系エンドポイントの保護: HTTP経由での状態変更（Mutation）操作は、本番・開発を問わず認証の付与を既定で必須（Mandatory）とする。認証をバイパスした実行は、ローカル単体テスト環境において明示的にオプトイン指定した場合にのみ制限する。

12.2 プライバシー保護とログ設計

本計画では、巨大な外部オブザーバビリティ基盤を新規導入することは行わず、軽量な構造化ログを用いて追跡可能性を確保する。システムログはJSON形式での出力を標準とし、以下のフィールドを共通で付与する。

  • runId: 実行セッションの一意な識別子
  • deckId: 対象スライドデッキの識別子
  • revision: コンテンツのリビジョン番号
  • profile: 適用されたビルドまたは配信プロファイル
  • phase: 処理フェーズ（初期化、ビルド、配信、同期など）
  • error.code: 発生したエラーの標準化コード

ログ出力を行う際は、認証トークン、発表者ノートの本文、スライドのMarkdown本文、およびユーザー環境に依存するローカル絶対パスなどの機微情報をマスクまたは完全除去するフィルタを必ず通過させる。

13. ロールアウト

13.1 段階的移行計画

本計画の移行作業はローカル開発ワークスペース内での段階的移行を対象とし、クラウド環境への直接デプロイやnpmレジストリへのパッケージ公開は対象外とする。変更作業は以下の順序で実施し、既存の動作環境を損なわずに移行を進める。

  1. 新サービスの先行実装: 新設計のパッケージ（@slidev-stage-hub/*）へコアロジックを抽出し、単体での動作を確認する。
  2. ラッパーインターフェースの配置: 既存のエントリーポイントから新サービスを呼び出す薄いラッパーを配置し、外部契約を崩さずに切り替える。
  3. 新旧挙動の比較検証: 同一入力に対して新旧経路の出力結果を比較し、等価性を確認する。
  4. 旧内部経路の撤去: 互換性が確認された段階で、不要となった旧実装の内部パスおよび重複コードを安全に削除する。

13.2 コミットとリビジョン管理

Gitコミットは後述の8つの実装ステップと1対1で対応させ、独立したコミットとして履歴を管理する。これにより、特定ステップで問題が生じた際にも影響範囲を限定して安全に巻き戻せるようにする。 特にStep 1（フォーマッタ導入）においては、設定ファイルの追加コミットと、コードベース全体への一括フォーマット適用コミットを明確に分離する。静的検査ツールの導入差分とコード変更差分を混在させないためである。

また、既存のデータ管理においてデータベースのマイグレーションは不要である。過去に生成されたリビジョンデータ（Revision）はそのまま維持し、過去データの破壊や再変換を行わない設計とする。

13.3 スキーマ移行と切り戻し手順

Stage 機能のスキーマバージョン 2（schemaVersion 2、Discovery JSON のみ対象とし iframe bridge メッセージの protocolVersion 1 は維持）へ移行する際は、まず新しい Stage 実装で v1 と v2 の双方を解釈可能にした上で、Worker エンドポイント側で Schema v2（GET /native-player.json）を提供する順序でロールアウトする。古い Stage 実装が新設の v2 エンドポイントへ接続した場合は、未対応フィールドによる不整合を防ぐため明示的に接続を拒否（reject）する。新しい Stage 実装は既存の v1 エンドポイントに対しても互換動作を維持する。

検証段階で不整合や Gate 不通過が発生した場合の切り戻しは、該当する実装ステップ単位でコードをロールバックするとともに、設定ポインタを旧 config / previous site へ戻すことで対処する。本計画では R2 releases や Durable Objects の永続化データを削除・破壊しないため、旧バージョンの成果物と設定ポインタを保持することで安全に着手前の稼働状態へ復旧可能である。

  3. 独立作業の継続: 不通過となったGateと依存関係のない別コンポーネントの調査作業やドキュメント整理は継続して差し支えない。
  4. 未決事項による停止の禁止: 「Unclear Points」に定義された外部公開やライセンス等の未決事項を理由として、最終実装Gate（Gate G8）の判定を停止させてはならない。
