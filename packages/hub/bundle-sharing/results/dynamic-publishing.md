# R2アップロードによるSlidevスライド自動生成と版管理の設計調査メモ

> 追加調査：[Workersでのコンパイル](workers-compilation.md)。以下のContainer案は既存ビルドを流用する場合のもの。現在はユーザーの希望により、変換処理を分離してWorkersで実行する案を第一候補として調査している。

## 結論

既存の対応プロファイルを指定し、Markdownファイルや関連画像をCloudflare R2へアップロードするだけでスライド資料を公開する運用は、アーキテクチャ設計として実現可能であると判断します。

ただし、「WebアプリケーションやCloudflare Workersの再デプロイが不要になること」と「スライドのコンパイル処理自体が不要になること」は明確に区別する必要があります。素のMarkdownファイルを静的バケットに配置するだけでは現行のアプリケーションで表示できず、何らかの実行環境でSlidevのコンパイル処理を経由しなければなりません。

本調査に基づく推奨構成は、非公開の入力用バケット（private R2 source）へのオブジェクト作成通知を契機にCloudflare Queuesを経由させ、Node.js実行環境（Cloudflare Containersまたは外部ビルドランナー）でビルドを実行した上で、生成物を公開用R2へ配置してWorkerや既存Web配信基盤から配信するパイプラインです。この構成を採ることで、Webアプリケーション本体のデプロイを伴わずに資料を更新でき、アップロード時に成果物を事前生成しておくことで初回閲覧時の生成待ちを避けやすくなります。生成処理に失敗した場合は、既存の公開版をそのまま維持して閲覧障害を回避します。

なお、本メモは2026-10-09時点の調査メモであり、実際の実装、概念実証（PoC）、実環境へのデプロイ、性能計測は今回実施していません。

## 方式比較

### 現在の実装と課題

現在の`slidev-lab`における実装状況と制約は以下のとおりです。

- **ビルド処理の現状**: `bundle-sharing/experiments/module-graph/build.mjs`は、ビルド時に配置されている資料を走査・列挙し、`deckIds`、資料ごとの動的インポート（dynamic import）、`catalog.json`、`native-player.json`、およびサムネイル画像を一括生成しています。実行時にMarkdownを動的に取得（fetch）してコンパイルする機能は備えていません。
- **Slidevの仕組み**: SlidevはMarkdownからVueコンポーネントへの変換、レイアウト適用、UnoCSSのスタイル解決、Viteによるビルドを組み合わせて動作します（[Slidevの設計思想](https://sli.dev/guide/why)）。同一のテーマを利用する場合であっても、新しいMarkdownを追加・変更する際にはコンパイル処理が必要です。そのため、素のMarkdownファイルを静的バケットに配置するだけでは、現行のアプリケーション上でスライドを表示できません（[Slidevの標準静的配信](https://sli.dev/guide/hosting)）。
- **プロファイル互換性の判定**: `profile-runtime.mjs`および周辺のマルチプロファイルビルド処理を含む仕組みにおける互換グループは、Slidev CLIおよびクライアントの厳密なバージョン、テーマのファイル内容、セットアップ処理、有効化された機能や設定値を厳格に考慮して定義されています。単にテーマ名が同一であるというだけでは互換性は保証されません（現状は52.15.2および53.0.0を対象として管理）。
- **共有チャンクの制約**: 現行の共有チャンク（shared chunk）は、グループ全体の資料を一括ビルドした結果として出力されています。後から任意の資料を追加して参照できる安定したランタイムAPIは未提供です。既存の仕組みをそのまま流用する初期段階ではグループ単位の再ビルドが必要となり、資料単位での差分生成を実現するには追加の境界設計が求められます。
- **Native環境のメタデータ連携**: Native環境の資料メタデータは接続設定時のスナップショットとして保持されています。メタデータ内に`revision`は存在するものの、現在の閲覧URLは版が固定されておらず、エントリーポイントも`/<deckId>/1`の形式を前提としています。このため、新しい版固定URLや解決方式を導入するには、接続プロトコルやURL構造の改修が必要です。また、Nativeの外部ローカルノートは「接続元オリジン + 資料ID + ページ番号」で識別されており、`revision`が変更された際は警告を表示する仕様で、ページ構成の変化に追従する自動的な同期機能はありません。

### 代替アプローチとの比較

資料の自動公開を実現するにあたり、他の方式と比較検討した結果は以下のとおりです。

1. **サーバーサイドレンダリング（SSR）方式との比較**\
   サーバー上でHTMLのみを動的に生成するSSR構成では、スライド内の`v-click`をはじめとするインタラクティブなアニメーションや操作が機能せず、クライアント側でJavaScriptを実行して状態を復元するハイドレーション（hydration）処理が不可欠です（[VueのSSRとハイドレーション](https://vuejs.org/guide/scaling-up/ssr.html)）。毎リクエストごとにSSRを実行するよりも、静的な成果物をビルドして版（revision）ごとにキャッシュ配信する構成の方が適していると判断します。また、初回アクセス時にオンデマンドで生成する構成も選択肢としては考えられますが、初回閲覧時の待機時間が発生する点や、複数ユーザーから同時にアクセスされた際の重複生成の調停が複雑になる課題があります。
2. **ブラウザ内コンパイル方式との比較**\
   ブラウザ側でMarkdown、Vue、UnoCSSを動的にコンパイルすれば、サーバー側でのビルド環境を不要にできます。UnoCSSにはブラウザ実行用のランタイムが存在します（[UnoCSS runtime](https://unocss.dev/integrations/runtime)）。しかし、コンパイラ群をブラウザへ配布することによる通信容量の肥大化、起動時のクライアントCPU負荷、動的importの解決、厳格なコンテンツセキュリティポリシー（CSP）への適合、既存Slidev機能との完全な互換性確保が課題となります。本件ではバンドルサイズの軽量化とNative環境での安定動作を重視しているため、ブラウザ内コンパイルは優先しません。
3. **標準Cloudflare Workersでのビルド可否**\
   現行のNode.jsおよびViteを前提としたビルド処理を、標準のCloudflare Workers環境内でそのまま実行できるとは言えません。Workersには仮想ファイルシステムとして[`node:fs`](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/)が提供されていますが、プロセスを生成する[`child_process`は非機能スタブ](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)として提供されており、Vite等の外部プロセス呼び出しを伴うビルドツールを動作させられません。そのため、既存のビルド処理を移植する実行環境としては、Linuxコンテナが利用できる[Cloudflare Containers](https://developers.cloudflare.com/containers/)や外部のビルドランナーを採用するのが堅実です。なお、Cloudflare Containersの利用には有料プランの契約が必要であり、実行費用やコンテナのコールドスタートに伴う冷間生成時間は現時点で計測されていません。

### 導入の段階的アプローチ

既存の運用から段階的に移行するため、以下の2段階で設計を進めるアプローチを検討します。

- **段階1（グループビルドの自動化）**:\
  現行のグループ一括ビルド処理をそのままビルド環境上で実行する自動化パイプラインを構築します。成果物はR2へ自動公開されるため、利用者の手動ビルドやWebサイト本体の再デプロイ作業は解消されます。ただし、内部的にはグループ全体の再ビルド処理が残るため処理対象の範囲が広く、資料単位の差分生成と比較した実際の処理時間差や差分ビルドの実現性は未検証です。
- **段階2（プロファイル別ランタイム事前ビルドと資料差分コンパイル）**:\
  プロファイル単位で共通のランタイム基盤を事前にビルドして配置しておき、Markdownの更新時には対象資料固有のJavaScript、CSS、メタデータのみを差分コンパイルして出力します。これを実現するには、VueやSlidev本体の重複読み込みを防ぐ外部参照機構、安定したランタイム境界の策定、スライド個別CSSの抽出、利用可能な機能や依存ライブラリの制限を定義する必要があります。この差分ビルドの実現性や既存テーマとの完全な互換性はまだ検証されていません。また、新規テーマの導入、未登録コンポーネントの使用、依存ライブラリの追加が発生した際には、新しいプロファイルの事前生成を要求する運用となります。

## 推奨構成と版管理の設計案

### パイプライン構成と処理フロー

推奨するアーキテクチャの処理の流れは以下のとおりです。

1. **アップロード**: 利用者はMarkdown本体や参照画像を非公開の入力バケット（private R2 source）へ配置します。
2. **イベント検知**: R2の[イベント通知機能](https://developers.cloudflare.com/r2/buckets/event-notifications/)（プレフィックスやサフィックスによる絞り込みに対応）がオブジェクト作成や上書きを検知し、Cloudflare Queuesへメッセージを送信します。
3. **ビルド実行**: キューからイベントを受信したNode.js実行環境（Cloudflare Containersまたは外部ビルドランナー）が起動し、指定されたプロファイルに基づいてビルドを実行します。
4. **成果物の配置**: ビルド完了後、生成された静的アセット群を公開用R2バケットへ保存します。
5. **配信**: Cloudflare Workersまたは既存のWeb配信基盤を経由して、クライアントへスライドを配信します。Webアプリケーション自体のデプロイは通常不要です。

### ダイジェストと版（リビジョン）の生成規則

安全な版管理を行うため、以下の粒度でダイジェスト値を算出して成果物のパスを決定します。

- **`profileDigest`**: Slidev CLIおよびクライアントの厳密なバージョン、テーマのコード実体、コンパイラ設定、セットアップスクリプト、プラグイン群、許可された機能一覧から算出するフィンガープリント。
- **`sourceDigest`**: Markdown本文だけでなく、スライド内で参照されている画像ファイルやインクルードファイル（`includes`）も含めて算出するフィンガープリント。
- **`artifact revision`**: `profileDigest`と`sourceDigest`等を組み合わせて生成する一意の識別子。

生成された成果物は、`releases/<deck>/<revision>/...`や`profiles/<digest>/...`のように変更されることのない固定キー（immutable key）へ保存します。全アセット、サムネイル、`catalog.json`、およびNative用メタデータの出力がすべて成功した段階で、公開用マニフェストファイル内の`current`参照先をアトミックに切り替えます。過去の版のファイル群は、現在閲覧中のセッション保護および障害時のロールバック用途としてバケット内に保持します。

### アップロード整合性とキューの冪等性制御

素材のアップロードおよび非同期キューの処理においては、以下の点に配慮した制御が必要です。

- **素材の完全性担保**: 画像やMarkdownなど複数ファイルにまたがるアップロードが行われる場合、一部の素材が欠けた状態でビルドが開始されないよう、マニフェストファイルまたは完了マーカー（completion marker）を最後にアップロードする運用ルール等を定めます。途中の不完全な素材で公開されることを防ぎます。
- **キューの冪等性と順序逆転の防止**: Cloudflare Queuesは[少なくとも1回の配信（at-least-once）](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)を提供し、[メッセージの順序は保証されません](https://developers.cloudflare.com/queues/reference/how-queues-works/)。そのため、同一リビジョンに対する処理は重複して実行されても問題のない冪等な設計にします。さらに、古い生成処理が遅れて完了した際に最新の公開版を過去の世代で上書き（巻き戻し）してしまわないよう、資料ごとの世代管理や処理の直列化、公開直前の最新世代チェックを設けます（Cloudflare Durable Objectsやデータベースの利用が候補）。なお、R2において独立した複数オブジェクトの更新はトランザクション処理にならないため、アトミックな単一トランザクションとして前提を置かない設計とします。

### キャッシュ戦略と整合性

配信時のキャッシュ設計では、ストレージとCDNの挙動の違いを考慮します。

- **キャッシュ設定の分離**: パスにリビジョンを含む変更不能（immutable）な成果物はブラウザおよびCDNで長期キャッシュします。一方で、最新版を指し示す`current`参照（マニフェスト等）は再検証（`no-cache`）または短期キャッシュを設定します。
- **ストレージ整合性とCDNキャッシュ**: [R2自体は強整合性を提供しますが、カスタムドメインを経由したCDNエッジのキャッシュでは古いデータが返される可能性](https://developers.cloudflare.com/r2/reference/consistency/)があります。また、成果物が生成される前にリクエストされて発生した404ステータスのネガティブキャッシュが残らないよう、キャッシュヘッダーの制御に注意が必要です。
- **オブジェクトバージョンの扱い**: [`R2Object.version`](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)は単一オブジェクトのアップロード状態を識別するための値であり、バケット全体の過去世代を保持・取得する履歴管理機能の保証と混同してはなりません。世代履歴の管理は、アプリケーション側で明示的に版付きのキーパスを分けて保存する方式を採用します。

### クライアント挙動とセキュリティ設計

閲覧時の安定性と安全性を確保するため、クライアントとアクセス制御を以下のように設計します。

- **セッション固定**: WebおよびNative環境の閲覧セッションは、閲覧開始時点のリビジョンに固定します。発表の途中で最新版が公開されても表示が切り替わることはなく、ユーザーによる明示的な再読み込みや再接続によって新しい版へ遷移します。
- **Nativeプレイヤーの整合性確保**: Nativeの表示実体と内部の`registry`や`clickTotals`が不整合を起こさないよう、同一のリビジョンに基づいて読み込む変更が必要です。また、既存のノート識別キー（接続元オリジン + 資料ID + ページ番号）は維持し、ページ構成が変更された場合は引き続き警告を表示して発表者の混乱を防ぎます。
- **セキュリティ境界の分離**: 生のMarkdownには発表者用ノート（note）やVueコンポーネントの記述が含まれる可能性があるため、非公開の入力バケット（private source）と公開配信用バケットを分離します。ビルドの実行対象は信頼できる投稿者および登録済みの安全なプロファイルに限定し、ソースに付属する任意のセットアップ処理や`npm install`を無条件に実行することは避けます。既存システムで閲覧認証が必要な場合は、生成された静的成果物に対しても同等のアクセス制御を適用します。

## 制約と今後の検証項目

本メモの内容は設計案の整理にとどまり、実機検証は行っていません。本番適用に向けた次のステップとして、以下のPoC（概念実証）の実施を推奨します。

1. **描画互換性とバンドルサイズの検証**: 既存プロファイルを適用した状態で、Markdown本文の更新、新規UnoCSSクラスの記述、テーマ提供コンポーネントの使用を行い、完全な互換性をもって表示できるか、およびバンドルサイズの増分が許容範囲に収まるかを確認する。
2. **関連メタデータの更新検証**: 画像ファイルの差し替えや資料追加を行った際に、`catalog.json`、サムネイル画像、Native用メタデータが抜け漏れなく正常に更新されるかを確認する。
3. **異常系における整合性の検証**: キュー通知の重複受信、ビルド完了通知の順序逆転、ビルド失敗といった異常ケースを擬似的に発生させ、公開マニフェストの整合性が保たれ、旧公開版が維持されるかを確認する。
4. **セッション保護と実行性能の計測**: 発表セッションの継続中に新しい版を公開し、NativeおよびWeb環境で閲覧中の版が固定されること、ならびにノート警告が正しく動作することを確認する。あわせて、Cloudflare Containersや外部ビルド環境における冷間起動（コールドスタート時）および温間起動時のコンパイル所要時間と、実行に伴うインフラ費用を実測する。
